# 验证基础 学习笔记（Cracking VLSI 第5章）

> **核心结论**：验证的本质不是"跑测试"，而是通过**验证计划（Verification Plan）→ 刺激生成（Stimulus Generation）→ 检查（Checking）→ 覆盖率（Coverage）**的闭环，把设计缺陷风险压到可接受水平。面对"如何验证某个设计"这类面试题，标准套路是：先理解规格 → 列出待验场景 → 选择方法学（定向/约束随机/断言/覆盖率）→ 设计刺激与检查 → 找出 corner cases。
>
> **记忆主线**：
> 1. **方法论四件套**：定向测试 vs 约束随机 → 自检测试 → 覆盖率驱动验证（CDV）→ 测试分级
> 2. **断言验证（ABV）**：在源头抓错、一处编写多处复用（仿真/形式/原型）
> 3. **设计验证三板斧**：2×2 交换机、单端口 RAM、4 位 ALU —— 场景怎么列、环境怎么搭
> 4. **环境架构**：事件驱动 vs 周期仿真、事务级验证（TBV）、参考模型、BFM、常用工具
> 5. **项目管理**：进度指标 → 完备性判定 → GLS → 功耗性能权衡

## 一、验证方法论核心概念

### Q1. 1.1 定向测试 vs 约束随机验证（Directed Testing vs Constrained Random Verification）

面试中常考的一对概念。**定向测试**：为设计中的每一个 feature 手写一条定向 test 去验证。**约束随机测试**：用约束随机发生器（constrained random generator）按照设计规格自动产生激励。

| 对比维度 | 定向测试（Directed Testing） | 约束随机验证（Constrained Random） |
| --- | --- | --- |
| 激励来源 | 手写，针对每个 feature 逐一编写 | 约束随机发生器自动产生，激励满足规格约束 |
| 优点 | 精确命中目标场景；corner case 可达性强；调试简单 | 覆盖大量组合空间；能发现"没想到"的 bug；人力成本低 |
| 缺点 | 工作量大；容易漏掉未想到的场景；覆盖空间有限 | 难覆盖到"深角"（hard to reach corner cases）；需要额外做覆盖率监控 |
| 适用 | 覆盖难以用随机到达的边界/角点场景 | 覆盖绝大部分验证空间 |

> **记忆**：推荐做法是**混用**——约束随机打主力覆盖大部分验证空间，定向测试补刀覆盖难到达的 corner cases。

### Q2. 1.2 自检测试（Self-Checking Tests）

**定义**：自检测试是能在测试结束时通过某种手段自行检查结果正确性的测试。

结果预测的两种常见方式：
1. **计算预测**：在 test 内自行计算出某次存储操作的预期结果；
2. **采集预测**：从 DUT 中收集信息（如 status registers 或其他信息）作为预期。

> **记忆**：自检测试 = 测试自带"判卷老师"，不依赖人工看波形判断对错，这是可回归（regression）测试套件的基本前提。

### Q3. 1.3 覆盖率驱动验证（Coverage Driven Verification, CDV）

**核心思想**：把验证计划中每个 feature / scenario 映射成一个**覆盖率监视器（coverage monitor）**，在仿真过程中收集覆盖率信息，用覆盖率数字驱动验证的执行与收尾。

关键要点（5 条）：

1. **覆盖率监视器的组成**：可以是基于采样的 covergroup（sample based），也可以是基于断言的属性覆盖（property based coverage）。
2. **三件套配合**：激励由**约束随机刺激发生器**产生；正确性由**功能检查器（functional checkers）**保证；所有已实现的覆盖率监视器持续**收集覆盖率**。
3. **累计覆盖率**：通常对设计跑多条 test 或多个随机种子（seed）的回归，把每条 test 的覆盖率合并（merge）得到累计覆盖率。若某些 corner case 用约束随机很难覆盖，就改用定向测试。
4. **覆盖率反哺**：覆盖率信息反馈测试与约束的质量，帮助**微调约束**，让随机激励生成更高效。
5. **覆盖率定义必须评审**：由于覆盖率定义是衡量验证进度与完成度的关键步骤，必须对照验证计划和设计规格评审其**完整性与正确性**。

> **注意**：CDV 中"覆盖率怎么定义"是最关键的一步——定义错了，后面所有进度和完成度判断都会失真。

### Q4. 1.4 测试分级（Test Grading）

**背景**：功能验证中会同时发展出两类测试资产——定向测试 + 带不同激励控制方式的约束随机刺激发生器；整个验证项目积累下来形成一套**测试套件（test suite）**，用于验证正确性、找 bug、收集覆盖率。

**测试分级的定义**：按多种标准对单条 test 的质量打分的过程，常见评分维度：

- 功能覆盖率命中（functional coverage hit）
- 发现的 bug 数量
- 仿真运行时间
- 维护难易度（ease of maintenance）

**目的**：从测试套件中识别出**高效测试**，从而打磨出对设计验证最高效的测试套件。

> **记忆**：测试分级 = 给每条 test 做 KPI 考核，淘汰低效测试，保留高效测试。

### Q5. 1.5 断言验证方法学（Assertion Based Verification, ABV）

**定义**：用**断言（assertion）**捕获特定设计意图（design intent）的方法学；这些断言随后用于仿真（simulation）、形式验证（formal verification）和/或原型验证（emulation）中，检查设计实现是否正确。ABV 可作为其他功能验证方法学的**补充**，提高验证效率。

断言的四大收益：

1. **源头抓错**：断言在设计错误发生处即报错，提升可观测性（observability），缩短调试时间；
2. **一处编写、多处复用**：同一组断言可同时用于仿真、形式分析和原型验证（emulation）；
3. **库资源丰富**：通用设计的大量断言可从断言库（assertion libraries）获取，易于移植到任何验证环境；
4. **反哺覆盖率**：以 property 形式编写的 SystemVerilog Assertions（SVA）还能用作覆盖（cover property），支持覆盖率驱动验证。

> **记忆**：ABV 四收益 = 抓错早 + 复用广 + 现成多 + 能覆盖。

## 二、设计验证实战：如何制定验证策略

### 2.1 通用答题思路（先记住流程）

面试官常给一个简单设计 + 规格（全加器、简单 ALU、缓存、多主总线、交换机等），让你定义验证策略并解释验证步骤。答题四步法：

1. **理解规格**：仔细读规格，有疑问先向面试官澄清；
2. **列出待验场景**：识别需要验证的场景，产出一份**验证计划和策略文档**——列出要验的 feature/scenario、用什么方法学（定向/约束随机、覆盖率、断言等）、如何检查正确性；
3. **细化实现**：说明刺激如何生成、检查如何完成；
4. **找 corner cases**：把设计所有 feature 过一遍，识别必须验证的边界情况。

### Q6. 2.2 案例 1：2×2 端口分组交换机（Packet Switch）

**设计规格**：
- 2 个输入端口 A、B 和 2 个输出端口 A、B；
- 每个端口可接收 64 ~ 1518 字节的可变长数据包；
- 每个包结构：4 字节源地址（SA）+ 4 字节目的地址（DA）+ 数据 + 4 字节 CRC（对整个包计算）；
- 根据目的地址把包切换到某个输出端口。

**① 需要验证的场景**：

| 场景 | 说明 |
| --- | --- |
| a. 正确交换 | 根据目的地址，包从 A 口正确交换到两个输出端口 |
| b. 不同包长 | 最小长度、最大长度、以及中间随机长度 |
| c. 地址全覆盖 | 源地址、目的地址的所有可能取值 |
| d. 不同数据模式 | 各种 data pattern |
| e. 流式发包 | 背靠背无延迟、间隔几个周期、间隔很多周期；连续相同长度 / 连续不同长度 |
| f. CRC 功能 | 检查输出的 CRC 是否符合预期（期望正确 CRC） |
| g. 比特翻转 | SA/DA/数据甚至 CRC 的某些位被破坏（corrupted）时的行为 |
| h. 延伸思考 | 还能想到什么？（多口同时发包、广播/组播、端口背压等） |

**② 验证环境搭建**：
- 设计一个**约束随机包发生器（constrained random packet generator）**产生上述场景；
- 需要一个 **scoreboard / checker** 检查包正确性与交换行为是否正确；
- 随机测试还需要写**覆盖率监视器**，确保上面列的重要场景都被覆盖到。

**③ 追问准备**：面试官可能继续让你实际写 SystemVerilog 的包发生器、checker 或 driver 代码。

> **注意**：这类题重点考察"思考的全面性"——场景清单越全越加分，最后留一个"What more can you think of?"的钩子展示发散思维。

### Q7. 2.3 案例 2：单端口 RAM

**规格要点**：单端口 RAM 只有一个端口供读和写，因此任意时刻只能做读**或**写；验证还需考虑 RAM 大小、地址总线与数据总线位宽。

**必须验证的 6 类场景**：

1. **单次读写**：单独读、单独写行为正确；
2. **背靠背操作**：对同一地址、不同地址的背靠背读/背靠背写；
3. **写后读**：同一地址背靠背"写→读"；
4. **读后写**：同一地址背靠背"读→写"；
5. **边界**：RAM 容量边界的读写（首地址/末地址）；
6. **写模式**：全 0、全 1、0/1 交替、walking one / walking zero 等不同写数据模式。

**环境设计延伸**：若被进一步要求定义验证环境，可基于以上场景判断**定向环境还是约束随机环境**更合适，并说明刺激发生器与 checker 如何设计。

### Q8. 2.4 补充：单端口 RAM vs 双端口 RAM（Single Port vs Dual Port RAM）

| 对比 | 单端口 RAM | 双端口 RAM |
| --- | --- | --- |
| 读写端口数 | 1 个（读/写共用） | 2 个读/写端口 |
| 并发能力 | 任意时刻只能读**或**写 | 允许**同时**读或写 |

> **记忆**：双端口 RAM 的价值就是并发访问——两个端口可同时读/写。

### Q9. 2.5 案例 3：4 位 ALU

**设计规格**：支持两个 4 位操作数（A、B）、4 位结果总线、进位溢出（carry overflow）；用 3 位 opcode / 选择线（S2 S1 S0）译码，最多支持 8 条指令。

**需要验证的 7 类场景**：

1. **单指令功能**：驱动操作数 A、B 和每条指令对应的选择线，验证所有单独操作（Add、Sub、Increment、AND、OR）正确；
2. **非法 opcode**：选择线为 110~111 时，不发生任何操作；
3. **极值组合**：对每条指令取 A、B 的最小/最大值及其组合（A、B 为 4 位，最大值 4'b1111）；
4. **溢出/下溢**：ADD 时 A、B 均为 4'b1111 会发生溢出；SUB 时 B > A 会发生下溢；
5. **回绕**：Increment 指令的环绕——A = 4'b1111 时加 1 应得到 0；
6. **指令序列**：单场景验证通过后，产生**随机 opcode 序列**，验证一条操作不影响后续操作；覆盖同一 opcode 连续重复、不同 opcode 按不同模式重复的序列；
7. **环境搭建**：刺激用随机 opcode + 操作数发生器加简单 driver；检查用**简单 ALU 参考模型**（simple model/ALU），把输出与模型结果对比。

> **记忆**：ALU 验证 = 单指令功能 → 非法码 → 极值 → 溢出/回绕 → 随机序列干扰 → 参考模型比对。

## 三、仿真器与验证环境

### Q10. 3.1 事件驱动 vs 周期仿真器（Event Driven vs Cycle Based Simulator）

| 对比维度 | 事件驱动仿真器 | 周期仿真器 |
| --- | --- | --- |
| 工作原理 | 对每个事件（输入激励的任何变化）求值，把变化在设计内传播直至**稳态**；同一周期内设计元素可能因输入到达时刻不同、下游反馈而被求值多次 | 时钟周期内没有"时间"概念，对状态元素/端口之间的逻辑**一次求值** |
| 速度 | 较慢（一次周期可能多次求值） | 快（每个逻辑元素每周期只求值一次，显著提升速度） |
| 精度 | 准确，能捕捉毛刺（glitch） | 无法检测信号毛刺；只对**全同步设计**效果好 |
| 时序验证 | 仿真本身包含时序 | 不考虑时序，需另行用静态时序分析（STA）工具做时序验证 |
| 代表工具/使用 | Questa（Mentor）、VCS（Synopsys）、Incisive（Cadence）——工业界主流 | 通用设计用得少，多为定制；大型设计（如微处理器）公司内部使用 |

**事件驱动工作原理举例**：两个触发器之间的组合逻辑路径（含多个门和反馈路径）。时钟沿到来、第一级触发器输出变化 → 施加到逻辑路径输入端 → 组合逻辑各级输入变化依次触发对应设计元素求值 → 可能需要多次求值，直到该时钟周期内数值稳定不再变化。

> **注意**：周期仿真快的代价是"看不见毛刺、只认同步逻辑"——这也是它无法取代事件驱动仿真的原因。

### Q11. 3.2 事务与事务级验证（Transaction / Transaction based Verification）

**事务（Transaction）**：一组底层信息（如一组信号）的**高层抽象**。

**分层架构思想**：设计在信号级工作，因此 testbench 中与设计交互的 driver、monitor 必须处于信号级；而 testbench 的其他部分都可以抽象到事务级，形成**分层（layered）架构**——只有最底层组件在信号级工作，其余组件基于事务通信。

事务级验证的三大好处：

1. **组件可复用**：具备事务接口的组件可在项目内或跨项目的不同验证环境中复用。例如：只有 driver、monitor、responder 需要信号级接口；一旦它们把信号级信息打包成事务，stimulus generator、slave model、scoreboard 等都能在事务级工作；
2. **仿真更快**：仿真器只需在**事务边界**上对事务级组件求值，而不是每次信号变化都求值；
3. **抗接口变更**：如果设计的接口时序改变，只需修改 driver 和 monitor，其余组件不受影响。

> **记忆**：事务级验证 = 底层信号打包成事务 → 上层组件全部事务化 → 换来复用、提速、抗变更三大收益。

### Q12. 3.3 常用仿真 / 调试 / 形式验证工具

这是考察工具认知度的通用题，没有固定答案，但常见工具如下（回答后可能被追问使用感受、易用性/局限性）：

| 类别 | 常用工具 |
| --- | --- |
| 仿真器（Simulator） | Questa（Mentor Graphics）、VCS（Synopsys）、Incisive Simulator（Cadence） |
| 调试（Debug） | Verdi（Synopsys）、DVE |
| 形式验证（Formal） | Jasper（Cadence）、QuestaFormal（Mentor Graphics） |

### Q13. 3.4 参考模型（Reference Model）

**定义**：通常是**不可综合（non-synthesizable）**的设计规格模型，一般用 C / SystemVerilog 等高级语言编写。实现精度有两种选择：**周期级精度**（cycle level accuracy）或**更高层边界精度**（higher level boundary）。

**精度选择的例子**：
- CPU / 微处理器参考模型：应在**指令边界**精确建模状态；
- AMBA 总线协议参考模型：应按协议做到**周期精确**（cycle accurate）。

**用途**：参考模型通常用在 checker / scoreboard 中，为给定的激励模式产生**期望响应（expected response）**，再与设计输出的实际结果比对。

> **记忆**：参考模型 = 用高级语言写的"设计规格的黄金模型"，专门用来生成期望值供比对。

### Q14. 3.5 总线功能模型（Bus Functional Model, BFM）

**传统定义**：用 C / SystemVerilog 等高级语言编写的**不可综合模型**，模拟总线接口的功能，可连接到设计接口用于仿真设计。BFM 的两侧接口：
- 一侧：在**信号级**实现总线协议（protocol）；
- 另一侧：提供**收发事务**的接口（transaction level）。

**定义演变**：随着方法学演进（如 UVM），已没有真正意义上的 BFM 组件，其功能由一组组件共同实现——如 **driver、monitor、receiver**。

> **记忆**：BFM = 信号级协议 + 事务级接口的两面模型；在 UVM 里被 driver/monitor/receiver 组合取代。

## 四、验证项目管理

### Q15. 4.1 验证进度跟踪与指标（Tracking Verification Progress）

**验证计划（Verification Plan）**捕获什么：
- 需要验证的场景/feature：以定向测试形式，或以详细场景与 corner cases 的**功能覆盖率监视器**形式；
- 验证环境开发的细节：刺激生成方法与检查方法学。

**不同阶段的进度指标**：

| 阶段 | 跟踪指标 |
| --- | --- |
| 项目早期 | 环境开发的完整度（stimulus generator、checker、monitor 等）、测试开发进度、功能覆盖率监视器开发进度 |
| 中期之后（测试与约束随机发生器基本就绪） | 在服务器农场（farm of servers）上跑回归，监控：**回归通过率（regression pass rates）、bug 率（bug rate）、功能覆盖率数字** |

> **记忆**：早期盯"建了什么"，后期盯"跑得怎样"——回归通过率 + bug 率 + 覆盖率三件套。

### Q16. 4.2 验证完备性：何时算验证完成？（Verification Completeness）

**理想定义**：当设计实现行为与设计规格完全一致、无任何错误时，功能验证才算完成。做法是对设计施加刺激覆盖**每一个可能的输入场景**，并验证设计无误。

**为什么理想不可行**：
- 设计复杂度不断上升，**穷举所有输入刺激场景**在实践上不可能；
- 资源与时间限制也使这一定义不现实。

**实际做法**：验证完备性 = 通过一组指标和流程获得的**置信度（confidence）**，把存在设计缺陷的风险降到最低。常用指标与流程（8 条）：

1. **评审验证计划与设计规格**：确保所有细节都被理解并捕获；
2. **开发完整性对照**：对照评审过的计划，确保环境开发、测试开发、功能覆盖率监视器开发都完整；
3. **实现评审**：评审 testbench 的刺激发生器与约束、checker、断言、覆盖率监视器的实现；
4. **回归稳定**：所有测试在回归模式下启用，连续数周无失败；所有覆盖率指标达成且被理解；
5. **bug 清零**：bug 率与未解决 bug 为零，或已充分理解且确认对设计无影响；
6. **波形审查**：对重要场景做波形审查（Waveform Review）；
7. **形式验证**：在可行处完成形式验证；
8. **横向对比**：与过往类似复杂度的成功项目对比**新 bug 流入率与 bug 趋势**。

> **注意**：面试时回答"验证何时完成"，先承认理想定义不可行，再落到"置信度 + 指标 + 流程"的实际答案，才显成熟。

### Q17. 4.3 门级仿真（Gate Level Simulation, GLS）

**定义**：RTL 综合成**门级网表（Gate Level Netlist）**之后运行的仿真。

**为什么必要**：GLS 是验证生命周期的重要部分。静态验证工具如 **STA（Static Timing Analysis）** 和 **LEC（Logical Equivalence Checking）** 无法覆盖/报告所有问题，所以 GLS 必不可少。

**GLS 的 5 大主要用途**：

1. 验证 **DFT 扫描链**（scan chains）；
2. 验证**异步设计**中的关键时序路径（这是 STA 不做的）；
3. 验证 **Reset 与上电流程**（Reset and Power Up flows）；
4. 分析 RTL 中的 **X 态乐观**（X-State Optimism）；
5. 收集**开关活动**（Switching Activity）用于功耗估算。

> **记忆**：GLS 用途五连——扫链、异步关键路径、复位上电、X 态乐观、功耗活动。

### Q18. 4.4 功耗与性能权衡（Power and Performance Trade-offs）

**基础公式**：动态功耗（dynamic power）正比于 **CV²f**（f = 频率，V = 电压，C = 电容）。

两条基本权衡规律：

| 调整手段 | 对功耗 | 对性能 |
| --- | --- | --- |
| 降低电压 V | 降低功耗 | 性能下降（延迟增大） |
| 降低频率 f | 降低功耗 | 性能下降（时钟变慢） |

**结论**：理想产品希望"性能最高 + 功耗最低"，但实际不可兼得。要到达最优的功耗/性能目标，设计必须在**电压与频率取值**上做出正确选择。

> **注意**：关于功耗与时钟的更多问题，见下一章（Verification Methodologies）的 "Power and Clocking" 小节（6.3）。

### 最重要的 10 条规则

| # | 规则 |
| --- | --- |
| 1 | 拿到设计题先**理解规格、澄清疑问**，再列场景、出验证计划，最后才谈工具和环境。 |
