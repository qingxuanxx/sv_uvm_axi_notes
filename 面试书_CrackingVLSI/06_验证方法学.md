## 6.1 UVM（Universal Verification Methodology）

> 本节恢复为原书 Q1～Q66 的提问顺序。原先按 TLM、sequence、driver、factory 等主题归类的内容均保留在对应问题中。

### Q1. 什么是 UVM？它有哪些优点？

**UVM（Universal Verification Methodology，通用验证方法学）** 是验证行业日益普及的标准验证方法学，由 Accellera 创建，目前正由 IEEE 1800.2 工作组标准化。它既定义了构建 testbench 和测试用例的方法论，也提供了一整套类库，帮助工程师快速搭建高效的约束随机 testbench（constrained random testbench）。

UVM 的优势与关注点：

| 优点 | 说明 |
|---|---|
| **模块化与可复用** | 方法学按模块化组件设计（Driver、Sequencer、Agent、Env 等），组件可从单元级复用到多单元级、芯片级验证，也可跨项目复用 |
| **测试与 testbench 分离** | 测试（激励/sequence）与实际 testbench 层次分离，激励可在不同单元或项目间复用 |
| **仿真器无关** | 基类库和方法学被所有主流仿真器支持，不依赖特定仿真器 |
| **激励生成能力强** | sequence 机制对激励生成有良好控制：随机化、分层 sequence、virtual sequence 等多种方式 |
| **配置机制简化层次配置** | 可轻松配置层次很深的 testbench 组件，无需关心组件在层次中的位置 |
| **factory 机制简化组件修改** | 通过 factory 创建组件，可在不同测试或环境中覆盖（override）组件类型而无需修改底层代码 |

> 记忆：UVM 六大优点可记为一句话——**"模复分仿激配"（模块化复用、测试分离、仿真器无关、激励可控、配置简化、factory 可覆盖）**。

### Q2. UVM 的缺点有哪些？

1. **学习曲线陡峭**：对新手而言，理解方法学全部细节和类库需要较长时间。
2. **方法学仍在发展、开销较大**：框架本身有一些开销，有时会让仿真显得较慢，也可能存在一些框架自身的 bug。

> 注意：尽管有缺点，随着 UVM 在验证行业中的广泛采用，其优点远大于缺点。

### Q3. 什么是事务级建模（TLM）？

**事务级建模（Transaction Level Modelling, TLM）** 是在更高抽象层次上对系统或设计建模的方法。在 TLM 中，模块之间的通信用**事务（Transaction）** 来建模，从而抽象掉所有底层实现细节。

- 即使 DUT 的真实接口是信号级活动，大部分验证任务——生成激励、功能检查、收集覆盖率数据——更适合在**事务级**完成，使其独立于具体信号级细节。
- 这样做让这些组件更容易复用、更易维护，跨项目也更好移植。

> 记忆：TLM 的核心思想 = **"用事务通信，把信号细节藏起来"**，是验证方法学提高模块化和复用生产力的关键概念之一。

### Q4. 什么是 TLM port 和 export？

- **TLM port**：定义了一组用于特定连接的方法（API），是发起通信的一端。
- **TLM export**：这些方法的**实际实现**，是接收通信的一端。
- port 与 export 之间的连接就建立了两组件间的通信机制。

例如：生产者（producer）创建事务并 `put()` 到 TLM port 上；`put` 方法的实现（即 TLM export）位于消费者（consumer）中，消费者读取生产者创建的事务，从而建立通信通道。

### Q5. 什么是 TLM FIFO？

当生产者与消费者需要**独立运行**时，使用 **TLM FIFO** 进行事务级通信：生产者生成事务并 `put` 进 FIFO，消费者每次从 FIFO 取出一个事务并处理。

> 记忆：TLM FIFO = 生产/消费解耦的缓冲通道，两端的运行速度可以不同。

### Q6. get() 与 peek() 的区别

- **get()**：从 TLM FIFO 返回一个事务（若有），并**将其从 FIFO 中移除**。若 FIFO 为空，则**阻塞**等待直到至少有一个条目。
- **peek()**：从 TLM FIFO 返回一个事务（若有），但**不移除**该事务。同样是阻塞调用，FIFO 无条目时等待。

> 记忆：get = 取走（destructive），peek = 偷看（non-destructive）。

### Q7. get() 与 try_get() 的区别

- **get()**：阻塞调用，FIFO 无条目时会一直等待，暂停执行。
- **try_get()**：非阻塞调用，即使 FIFO 无条目也立即返回；返回值指示是否取到了有效条目。

两种等效实现：

```systemverilog
// 1) 使用阻塞方法 get()
class consumer extends uvm_component;
  uvm_get_port #(simple_trans) get_port;
  task run;
    for (int i = 0; i < 10; i++) begin
      t = get();  // 阻塞，直到返回一个事务
      // 处理该事务
    end
  endtask
endclass

// 2) 使用非阻塞方法 try_get() 的等效实现
class consumer extends uvm_component;
  uvm_get_port #(simple_trans) get_port;
  task run;
    for (int i = 0; i < 10; i++) begin
      // try_get 非阻塞，所以每个周期持续尝试
      // 直到返回 true
      while (!get_port.try_get(t)) begin
        wait_cycle(1);  // 等待一个时钟周期的任务
      end
      // 处理该事务
    end
  endtask
endclass
```

> 注意：阻塞版本代码更简洁；非阻塞版本需轮询，但在需要"边等边做别的事"的场景下更灵活。

### Q8. Analysis port/FIFO 与 TLM port/FIFO 的区别

- **TLM port/FIFO**：用于两个组件之间建立 put/get 通信通道的**一对一**事务通信。
- **Analysis port/FIFO**：用于一个组件向**多个**组件分发（广播）事务的通信通道。

典型用途：

- **TLM port/FIFO**：driver 与 sequencer 之间的连接。
- **Analysis port/FIFO**：monitor 广播事务，供 scoreboard 或覆盖率收集组件接收。

> 记忆：TLM = 点对点（put/get）；Analysis = 一对多广播（subscribe/observer 模式）。

### Q9. sequence 与 sequence item 的区别

- **sequence item**：建模两个组件间传输信息的对象（也可称为事务）。例如 CPU 访问主存的读/写事务，包含地址、数据、读写类型等信息。
- **sequence**：一系列 sequence item 的**定义好的模式**，发送给 driver 注入设计。该模式由 sequence 中 `body()` 方法的实现决定。例如：定义一个"10 次对递增地址的读事务"的 sequence，其 `body()` 会生成 10 个 sequence item 发送给 driver，每个 item 之间地址递增或随机化。

> 记忆：item = 单个事务数据；sequence = item 的组织模式（由 body() 决定）。

### Q10. uvm_transaction 与 uvm_sequence_item 的区别

- **uvm_transaction**：建模任何事务的基类，派生自 `uvm_object`。
- **uvm_sequence_item**：本质是一种事务，除了把一些信息打包在一起，还附加额外信息，如 **sequence id**（生成该 item 的 sequence 的 id）和 **transaction id**（该 item 自身的 id）。

推荐：实现基于 sequence 的激励时使用 **uvm_sequence_item**。

> 记忆：sequence_item = transaction + sequence id + transaction id。

### Q11. copy()、clone()、create() 的区别

1. **create()**：构造一个对象。
2. **copy()**：把一个对象复制到另一个对象。
3. **clone()**：一步完成"创建 + 复制"——先调用 `create()` 创建对象，再调用 `copy()` 把现有对象复制到新句柄，返回新对象。

> 记忆：clone = create + copy 的组合拳。

### Q12～Q13. 什么是 Agent？Agent 可以包含哪些组件？

**UVM agent** 是围绕 DUT 某个**特定引脚级接口**组织起来的一组 uvm_component 的集合。大多数 DUT 有多个逻辑接口，agent 把在该接口上工作的所有 driver、sequencer、monitor 及其他组件归为一组。这种层次组织方式使得"接口相同的 agent"可以在不同验证环境和项目间复用。

一个 agent 通常包含：

- **driver 和 sequencer**：在该接口上向 DUT 驱动激励；
- **monitor 和 analysis 组件**（如 scoreboard 或覆盖率收集器）：分析该接口上的活动；
- **配置对象**：配置 agent 及其内部组件。

### Q14. get_name() 与 get_full_name() 的区别

- **get_name()**：返回对象的名字，即构造函数 `new` 的 name 参数或 `set_name()` 设置的名字。
- **get_full_name()**：返回对象的**完整层次名**。对 uvm_component 而言，打印时能显示完整层次结构，非常有用；对 sequence 或 config 对象（无层次），返回与 get_name() 相同。

### Q15. ACTIVE agent 与 PASSIVE agent 的区别

- **ACTIVE agent**：能够在所操作的引脚级接口上**产生活动**。driver 和 sequencer 会被创建并连接，会有 sequence 在其上运行以产生激励。
- **PASSIVE agent**：**不产生任何活动**，只监视接口上发生的事件。driver 和 sequencer 不会被创建。

典型用法：块级验证环境需要生成激励，agent 配为 **ACTIVE**；到芯片级验证环境不再需要生成激励（但仍需监视活动用于调试或覆盖率），同一个 agent 可配置为 **PASSIVE** 复用。

### Q16. 如何把 agent 配置为 ACTIVE 或 PASSIVE？

UVM agent 有一个 `UVM_ACTIVE_PASSIVE_e` 类型的变量 `active`，默认值为 `UVM_ACTIVE`。可以在 env 类创建 agent 时用 `set_config_int()` 修改，agent 的 build_phase 中按如下代码**有条件地创建 driver 和 sequencer**：

```systemverilog
function void build_phase(uvm_phase phase);
  if (m_cfg.active == UVM_ACTIVE) begin
    // 创建 driver、sequencer
  end
endfunction
```

> 记忆：ACTIVE = 建 driver+sequencer；PASSIVE = 不建 driver+sequencer，只留 monitor。

### Q17. sequencer 和 driver 是什么？为什么需要？

- **Driver**：把事务/sequence item 按照信号接口协议转换成一组**引脚级翻转**的组件。
- **Sequencer**：把 sequence item 从 sequence 路由到 driver，并把响应从 driver 路由回 sequence；还负责处理多个 sequence（若存在）争用 driver 的**仲裁**。

它们之所以必要，是因为在 UVM 这种 TLM 方法学中，激励生成被抽象为事务级，sequencer 和 driver 负责路由事务并将其翻译为真实的引脚翻转。

### Q18. monitor 与 scoreboard 的区别

- **Monitor**：观察引脚级活动，把观察结果转换成事务/sequence_item，并通过 analysis port 发送给 analysis 组件。
- **Scoreboard**：一种 analysis 组件，检查 DUT 行为是否正确。UVM scoreboard 使用 agent 内 monitor 发出的 analysis 事务来比对。

> 记忆：monitor = 观察并转换（采样）；scoreboard = 比对并判定（检查）。

### Q19. run_test() 如何启动 testbench？

**run_test()** 是一个**静态方法**，用于激活 UVM testbench。通常在顶层 test module 的 `initial begin ... end` 块中调用，参数指定要运行的 test 类。它会触发 test 类的构造，随后执行 `build_phase()`，进而构造 testbench 层次中的 Env/Agent/Driver/Sequencer 等对象。

### Q20. 运行一个 sequence 需要哪些步骤？

三步：

1. **创建 sequence**：用 factory 的 create 方法创建：

```systemverilog
my_sequence_c seq;
seq = my_sequence_c::type_id::create("my_seq");
```

2. **配置或随机化 sequence**：sequence 可能有多个数据成员需要配置或随机化，可配置值或调用 `seq.randomize()`。
3. **启动 sequence**：调用 `sequence.start()`，参数为运行该 sequence 的 sequencer 指针。启动后 `body()` 方法被执行，决定 sequence 如何运行。`start()` 是阻塞的，直到 sequence 执行完才返回。

### Q21. sequencer 与 driver 之间的协议握手是怎样的？

UVM sequence-driver API 主要在 sequence 侧和 driver 侧各用两个方法完成一次 item 传输（及响应回收）：

**sequence 侧：**

1. `start_item(<item>)`：向 sequencer 请求对 driver 的访问权，driver 授予访问权后返回。
2. `finish_item(<item>)`：使 driver 收到该 item；阻塞方法，直到 driver 调用 `item_done()` 才返回。

**driver 侧：**

1. `get_next_item(req)`：driver 的阻塞方法，阻塞直到从连接 sequencer 的端口收到 sequence item；返回的 item 由 driver 翻译成引脚级协议。
2. `item_done(req)`：driver 用这个**非阻塞**调用通知 sequencer：可以解除 sequence 的 `finish_item()` 阻塞——无论是 driver 接受了请求还是已执行完该请求。

**其他可选方式：**

- driver 的 `get()` 方法等价于 `get_next_item()` + `item_done()`。
- 如果 driver 返回的响应信息超出请求类所能封装的内容，需要单独的**响应端口（response port）**：sequencer 用阻塞方法 `get_response()`，driver 用 `put()` 在该端口发送独立响应来解除其阻塞。

> 记忆：握手口诀 —— sequence 侧 **start_item → finish_item**，driver 侧 **get_next_item → item_done**，两两配对、一收一放。

### Q22. pre_body() 和 post_body() 是什么？它们总会被调用吗？

- **pre_body()**：在 sequence 的 `body()` 被调用**之前**调用。
- **post_body()**：在 `body()` 被调用**之后**调用。
- 它们**并不总是被调用**：`uvm_sequence::start()` 有一个可选参数 `call_pre_post`，若置为 0，则不会调用这两个方法。

`start()` 的形式参数：

```systemverilog
virtual task start(
  uvm_sequencer_base sequencer,              // 指向 sequencer 的指针
  uvm_sequence_base parent_sequencer = null, // 父 sequencer
  integer this_priority = 100,               // 在 sequencer 上的优先级
  bit call_pre_post = 1                      // 是否调用 pre_body/post_body
);
```

### Q23. start() 是阻塞还是非阻塞？

**阻塞**。`start()` 会一直阻塞执行，直到 sequence 的 `body()` 执行完毕。

### Q24. sequencer 有哪些仲裁机制？

多个 sequence 可以并发地与连接同一接口的 driver 交互，sequencer 通过仲裁机制保证**任意时刻只有一个 sequence 能访问 driver**。用 `set_arbitration()` 方法选择算法，共 6 种：

| 仲裁模式 | 行为 |
|---|---|
| **SEQ_ARB_FIFO**（默认） | 按 FIFO 顺序从所有运行中的 sequence 取 item（seq1 → seq2 → seq3 → 循环） |
| **SEQ_ARB_WEIGHTED** | 始终先取最高优先级 sequence 的 item，取完再取次高优先级；同优先级时随机顺序 |
| **SEQ_ARB_RANDOM** | 忽略所有优先级，从各 sequence 随机取 item |
| **SEQ_ARB_STRICT_FIFO** | 类似 WEIGHTED，但同优先级时按 FIFO 顺序而非随机 |
| **SEQ_ARB_STRICT_RANDOM** | 类似 RANDOM，但不忽略优先级：先从最高优先级随机取，再下一级 |
| **SEQ_ARB_USER** | 用户自定义算法：扩展 uvm_sequencer 类并重写 `user_priority_arbitration()` 方法 |

> 记忆：FIFO 看顺序、WEIGHTED 看优先级、RANDOM 全随机、STRICT_* 是"优先级+有序"的组合，USER 自己写。

### Q25. 如何指定 sequence 的优先级？

把优先级作为参数传给 `start()` 方法（第三个参数），优先级由各 sequence 的相对值决定：

```systemverilog
seq_1.start(m_sequencer, this, 500);  // 最高优先级
seq_2.start(m_sequencer, this, 300);  // 次高优先级
seq_3.start(m_sequencer, this, 100);  // 三者中最低优先级
```

### Q26. 如何让 sequence 独占 sequencer？

有时 sequence 需要在全部 item 驱动完之前独占 sequencer（例如要无中断地激励一个确定性模式），两种机制：

1. **lock() / unlock()**：sequence 调用所在 sequencer 的 `lock()`。调用 sequence 通过仲裁机制获得下一个时隙后被授予独占访问权；若存在更高优先级的 sequence 需先等待。lock 授予后，其他 sequence 无法访问 driver，直到该 sequence 调用 `unlock()` 释放。`lock()` 是阻塞的，授予前不返回。
2. **grab() / ungrab()**：与 lock 类似，但 **grab() 立即生效**——直接抢下下一个仲裁时隙，**无视任何优先级**。唯一能阻止 grab 的是 sequencer 上已存在的 lock() 或 grab() 条件。

### Q27. grab() 与 lock() 的区别

| | lock() | grab() |
|---|---|---|
| 生效方式 | 需等待按优先级/仲裁机制轮到自己的下一个时隙 | 立即生效，抢下下一个仲裁时隙 |
| 是否受优先级影响 | 是（高优先级 sequence 可先获得） | 否（覆盖所有优先级） |
| 使用类比 | 可屏蔽中断（prioritized interrupt） | 不可屏蔽中断（NMI） |

> 记忆：lock 讲礼貌排队，grab 不讲武德直接抢。

### Q28. 流水线（pipelined）与非流水线（non-pipelined）驱动模型

根据接口需要，UVM driver 类可实现两种模式：

**非流水线模型**：driver 同一时刻只建模一个活动事务。sequence 发一个事务后，driver 要花多个周期（依接口协议而定）完成驱动，之后才接受新事务。

```systemverilog
class nonpipe_driver extends uvm_driver #(req_c);
  task run_phase(uvm_phase phase);
    req_c req;
    forever begin
      get_next_item(req);  // 通过 sequencer 从 sequence 获取 item
      // 驱动请求到 DUT，可能耗时多个时钟
      // 在此之前 sequence 被阻塞，无法发送新 item
      item_done();         // ** 解除 sequence 中 finish_item() 的阻塞
    end
  endtask : run_phase
endclass : nonpipe_driver
```

**流水线模型**：driver 同时建模**多个活动事务**。sequence 无需等待 driver 完成上一个事务即可持续发送新事务。driver 每次收到事务后 `fork` 一个独立进程去驱动接口信号，自己不等待其完成就接受新事务。适用于希望**背靠背（back-to-back）** 驱动请求、不等设计响应的场景。

```systemverilog
class pipeline_driver extends uvm_driver #(req_c);
  task run_phase(uvm_phase phase);
    req_c req;
    forever begin
      get_next_item(req);  // 通过 sequencer 从 sequence 获取 item
      fork
        begin
          // 驱动请求到 DUT，可能耗时多个时钟
          // 独立线程，不阻塞 sequence
          // driver 无需等待即可接受更多 item
        end
      join_none
      item_done();         // ** 解除 sequence 中 finish_item() 的阻塞
    end
  endtask : run_phase
endclass : pipeline_driver
```

> 记忆：non-pipelined = 一收一发；pipelined = fork 出去、立即 item_done、继续收。

### Q29. 多个 sequence 运行时，如何保证响应送回正确的 sequence？

sequencer 依据 sequence item 中的 **sequence id 字段**把响应路由回正确的 sequence。driver 的响应处理代码应调用 **set_id_info()**，确保响应 item 与发起请求具有相同的 sequence id：

```systemverilog
class my_driver extends uvm_driver;
  // 从 sequence 端口获取 item 并把响应发回
  function drive_and_send_response();
    forever begin
      seq_item_port.get(req_item);          // 从 sequence 端口获取 item
      drive_req(req_item);                  // 把 req_item 驱动到引脚
      rsp_item = new();                     // 创建新的响应 item
      rsp_item.data = m_vif.get_data();     // 从 DUT 监视响应信号
      rsp.set_id_info(req_item);            // 把 id 从 req 复制到 response
      rsp_port.write(rsp_item);             // 在 rsp 端口写响应
    end
  endfunction
endclass
```

### Q30～Q31. m_sequencer 与 p_sequencer 是什么？有何区别？

- **m_sequencer**：类型为 `uvm_sequencer_base` 的句柄，uvm_sequence 中**默认可用**，保存着 sequence 所运行的 sequencer 的引用。通过它，sequence 可以访问 UVM 组件层次中的信息和资源句柄。
- **p_sequencer**：sequence 是生命周期有限的对象（不像 sequencer/driver/monitor 等组件贯穿整个仿真），要访问 testbench 组件层次中的成员/句柄，需要把 `m_sequencer` **类型转换（$cast）** 成真实的 sequencer 类型，转换后的句柄习惯上叫 `p_sequencer`（名字可任取）。

```systemverilog
class test_sequence_c extends uvm_sequence;
  test_sequencer_c p_sequencer;
  clock_monitor_c my_clock_monitor;
  task pre_body();
    if (!$cast(p_sequencer, m_sequencer)) begin
      `uvm_fatal("Sequencer Type Mismatch:", " Wrong Sequencer");
    end
    my_clock_monitor = p_sequencer.clk_monitor;  // 通过 p_sequencer 访问 sequencer 里的句柄
  endtask
endclass

class test_Sequencer_c extends uvm_sequencer;
  clock_monitor_c clk_monitor;
endclass
```

> 记忆：m_sequencer = 默认的基类句柄；p_sequencer = 经 $cast 后的具体 sequencer 句柄，用于访问具体成员。

### Q32. 早期随机化（early randomization）与晚期随机化（late randomization）

- **早期随机化**：先调用 `randomize()` 随机化对象，再调用 `start_item()` 请求访问 sequencer（阻塞调用，耗时取决于 sequencer 忙闲程度）。

```systemverilog
task body();
  assert(req.randomize());
  start_item(req);  // 可能因 sequencer 仲裁而耗时
  finish_item(req);
endtask
```

- **晚期随机化**：先调用 `start_item()` 等待仲裁授权，**在把事务发给 sequencer/driver 之前**才调用 `randomize()`。好处是 item 在最后一刻才随机化，可以利用设计或其他组件的反馈。

```systemverilog
task body();
  start_item(req);  // 可能因 sequencer 仲裁而耗时
  assert(req.randomize());
  finish_item(req);
endtask
```

> 记忆：early = 先随机后请求；late = 先请求后随机（just-in-time，可用最新反馈）。

### Q33. 什么是 subsequence？

**subsequence** 是指**从另一个 sequence 中启动的 sequence**：在一个 sequence 的 `body()` 中调用另一个 sequence 的 `start()`，被启动的那个就是 subsequence。

### Q34. get_next_item() 与 try_next_item() 的区别

- **get_next_item()**：阻塞调用（driver-sequencer API 的一部分），阻塞直到有可处理的 sequence item，返回其指针。
- **try_next_item()**：非阻塞版本，无 item 可处理时返回 **null 指针**。

### Q35. get_next_item() 与 get() 的区别

- **get_next_item()**：阻塞获取 sequencer FIFO 中的 item 供 driver 处理；处理完后必须调用 `item_done()` 完成握手，才能请求下一个 item。
- **get()**：同样是阻塞获取 item，但**无需显式调用 item_done()**，get() 隐式完成握手。

> 记忆：get = get_next_item + item_done 的合并。

### Q36. get() 与 peek() 的区别（driver 类中）

- **get()**：阻塞获取 item，有 item 时解除阻塞，并**完成与 sequencer 的握手**。
- **peek()**：与 get 类似，阻塞直到有 item 可用，但**不会把请求从 sequencer FIFO 中移除**——多次调用 peek() 会返回同一个 item。

### Q37. item_done() 带参数与不带参数的区别

`item_done()` 是 driver 类中的**非阻塞**方法，用于在 `get_next_item()` 或 `try_next_item()` 成功后与 sequencer 完成握手：

- **不带参数**：仅完成握手，**不向 sequencer 响应 FIFO 放置任何内容**（无需返回响应时用）。
- **带参数**：传入响应 sequence_item 的指针，该响应会被放入 sequencer 响应 FIFO，sequence 可作为其发出请求的响应来处理。

### Q38. 哪些 driver 方法是阻塞的，哪些是非阻塞的？

| 阻塞（blocking） | 非阻塞（nonblocking） |
|---|---|
| get() | try_next_item() |
| get_next_item() | item_done() |
| peek() | put() |

> 记忆：阻塞的都有 next/item 含义（要等数据）；非阻塞的是"试探"和"回话"（try/item_done/put）。

### Q39. 下列哪个 driver 代码是错的？

```systemverilog
// 1) 正确
function get_drive_req();
  forever begin
    req = get();
    req = get();
  end
endfunction

// 2) 错误！
function get_drive_req();
  forever begin
    req = get_next_item();
    req = get_next_item();
    item_done();
  end
endfunction

// 3) 正确
function get_drive_req();
  forever begin
    req = peek();
    req = peek();
    item_done();
    req = get();
  end
endfunction
```

**2) 是错的**：`get_next_item()` 不能在调用 `item_done()` 之前连续调用两次，否则无法与 sequencer 完成握手。

### Q40. 如何停止 sequencer 上运行的所有 sequence？

sequencer 有 `stop_sequences()` 方法。**注意**：该方法不检查 driver 当前是否正在处理 sequence item——若 driver 此时调用 `item_done()` 或 `put()`，可能因 sequence 指针无效而产生 Fatal Error。因此调用 `stop_sequences()` 后，需确保 sequencer 线程被禁用（若是在 fork 中启动的）。

### Q41. sequence.print() 调用的是哪个方法？

**convert2string()**。建议实现该函数，返回对象的字符串表示（其数据成员的值），便于把调试信息打印到仿真器 transcript 或日志文件。

### Q42. 下面 sequence 代码有什么问题？

```systemverilog
task body();
  seq_item_c req;
  start_item(req);
  #10 ns;
  assert(req.randomize());
  finish_item(req);
endtask
```

**问题**：`start_item` 与 `finish_item` 之间不应加延时。start_item 一旦返回，sequence 就赢得仲裁并占用了 sequencer/driver；此后到 finish_item 之间的任何延时都会**占用 sequencer/driver 不放**，其他 sequence 无法使用。若多个 sequence 跑在同一接口上，延时越长，设计接口空闲越久。

> 注意：仲裁成功后应立即 finish_item，把"占用窗口"压到最短。

### Q43. 什么是 virtual sequence？有什么好处？

**virtual sequence** 是**跨多个 sequencer 协调激励生成**的 sequence。由于 sequence、sequencer、driver 都面向单一接口，几乎所有 testbench 都需要 virtual sequence 来协调不同接口间的激励与交互。在子系统级或系统级 testbench 中，virtual sequence 也用于以协调的方式执行单元级 sequence。

典型结构：virtual sequence 持有多个 sequencer 的句柄，每个 sequencer 连接一个 DUT 接口对应的 driver；virtual sequence 可以在每个接口上生成子 sequence（subsequence）并在对应的 sub-sequencer 上运行。

### Q44. 6.1.13 UVM 完整示例：单端口 SRAM 的 sequence + driver

题目：单端口 RAM 每个周期只能做一次读或写。`read_enable=1` 表示读，`write_enable=1` 表示写。用 UVM 写 sequence 和 driver 测试读写。

实现思路：先定义 sequence item 类，sequence 和 driver 再以它为事务通信。

**1) Sequence item** —— sequence 与 driver 之间通信的事务，应抽象出最终要驱动到 DUT 引脚上的所有信息：

```systemverilog
class rw_txn extends uvm_sequence_item;
  rand bit [7:0] addr;              // 事务地址
  typedef enum {READ, WRITE} kind_e; // 读或写类型
  rand kind_e sram_cmd;
  rand bit [7:0] datain;            // 数据
  `uvm_object_utils(rw_txn)         // 注册到 factory，便于动态创建

  function new(string name = "rw_txn");
    super.new(name);
  endfunction

  // 打印工具
  function string convert2string();
    return $psprintf("sram_cmd=%s addr=%0h datain=%0h", sram_cmd.name(), addr, datain);
  endfunction
endclass
```

**2) Sequence** —— 生成 10 个上述类型的事务发给 driver：

```systemverilog
class sram_sequence extends uvm_sequence #(rw_txn);
  `uvm_object_utils(sram_sequence)   // 注册到 factory

  function new(string name = "sram_sequence");
    super.new(name);
  endfunction

  // sequence 启动后执行的主 body 方法
  task body();
    rw_txn rw_trans;
    // 创建 10 个随机 SRAM 读/写事务并发送给 driver
    repeat (10) begin
      rw_trans = rw_txn::type_id::create(.name("rw_trans"), .contxt(get_full_name()));
      start_item(rw_trans);          // 启动仲裁，获取 sequencer 访问权
      assert(rw_trans.randomize());  // 随机化 item
      finish_item(rw_trans);         // 发送给 driver
    end
  endtask
endclass
```

**3) Driver** —— 接收上述事务并按其驱动 SRAM 协议：

```systemverilog
class sram_driver extends uvm_driver #(rw_txn);
  `uvm_component_utils(sram_driver)
  virtual sram_if vif;               // 封装 DUT 信号的接口

  function new(string name, uvm_component parent = null);
    super.new(name, parent);
  endfunction

  // Build phase：从 config_db 获取 virtual interface 句柄
  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual sram_if)::get(this, "", "sram_if", vif)) begin
      `uvm_fatal("SRAM/DRV", "No virtual interface specified");
    end
  endfunction

  // Run phase：实现 driver-sequencer API 获取 item
  // 根据读/写类型在 SRAM 接口上驱动对应引脚
  virtual task run_phase(uvm_phase phase);
    super.run_phase(phase);
    this.vif.read_enable  <= '0;
    this.vif.write_enable <= '0;
    forever begin
      rw_txn tr;
      @(this.vif.master_cb);
      seq_item_port.get_next_item(tr);  // 先从 sequencer 获取一个 item
      @(this.vif.master_cb);            // 等待一个时钟沿
      uvm_report_info("SRAM_DRIVER", $psprintf("Got Transaction %s", tr.convert2string()));
      // 解码 SRAM 命令，调用读或写函数
      case (tr.sram_cmd)
        rw_txn::READ  : drive_read (tr.addr, tr.dataout);
        rw_txn::WRITE : drive_write(tr.addr, tr.datain);
      endcase
      seq_item_port.item_done();        // 向 sequencer 完成握手
    end
  endtask : run_phase

  // 驱动 SRAM 读所需信号
  virtual protected task drive_read(input bit [31:0] addr, output logic [31:0] data);
    this.vif.master_cb.addr        <= addr;
    this.vif.master_cb.write_enable <= '0;
    this.vif.master_cb.read_enable  <= '1;
    @(this.vif.master_cb);
    this.vif.master_cb.read_enable  <= '0;
    data = this.vif.master_cb.dataout;
  endtask : drive_read

  // 驱动 SRAM 写所需信号
  virtual protected task drive_write(input bit [31:0] addr, input bit [31:0] data);
    this.vif.master_cb.addr        <= addr;
    this.vif.master_cb.write_enable <= '1;
    this.vif.master_cb.read_enable  <= '0;
    @(this.vif.master_cb);
    this.vif.master_cb.write_enable <= '0;
  endtask : drive_write
endclass
```

> 记忆：写 UVM 代码的三段式——**item 定义数据 → sequence 组织激励（body 里 create/randomize/start_item/finish_item）→ driver 翻译成引脚协议（get_next_item/case 驱动/item_done）**。

### Q45. 什么是 factory？

**factory** 是 UVM 中一张特殊的**查找表（look up table）**，所有 UVM 组件和事务都在其中注册。UVM 推荐用 factory 的 `create()` 方法创建组件和事务对象。用 factory 创建对象还能实现**类型替换**：不修改 testbench 结构或代码，就能用派生类型替换某类型的对象。

### Q46. 用 new() 和 create() 创建对象有何区别？

- **推荐使用 `::type_id::create()`**：内部会调用 factory 查找请求的类型，再调用构造函数 `new()` 真正创建对象。这样便于类型覆盖（type override）：测试中可指定使用基类或派生类，其他 testbench 组件无需改代码就能创建对应类型的对象。
- **new()** 只能创建给定类型的对象，**不允许运行时更换类类型**；用 new() 意味着要切换类型时必须修改 testbench 代码。

> 记忆：create() 走 factory 查表（可覆盖），new() 直接构造（写死类型）。

### Q47～Q48. 如何把类注册到 factory？为什么要注册？

- **uvm_sequence 类**用 **`uvm_object_utils`** 宏注册：

```systemverilog
class test_seq_c extends uvm_sequence;
  `uvm_object_utils(test_seq_c)
endclass
```

- **uvm_component 类**用 **`uvm_component_utils`** 宏注册：

```systemverilog
class test_driver_c extends uvm_component;
  `uvm_component_utils(test_driver_c)
endclass
```

**为什么要注册**：factory 的便利性在于 testbench 构建过程可在**运行时**决定创建哪种类型的对象，从而可用派生类替换基类而无需改动代码。若类未注册到 factory，就无法使用 `::type_id::create()` 来构造对象。

### Q49. 什么是 factory override？

**factory override** 允许在构造点用**另一个派生类替换某个类**。可用于改变 testbench 行为，而**无需编辑或重新编译** testbench 代码。

### Q50～Q51. type override 与 instance override 的区别

- **type override（类型覆盖）**：每当 testbench 层次中创建某个组件类类型时，都用替代类型创建——对该组件类型的**所有实例**生效。
- **instance override（实例覆盖）**：只覆盖组件的**某个特定实例**，该实例通过其在 UVM 组件层次中的位置引用。

关键限制：**只有 uvm_component 类有层次、可做实例级覆盖**；sequence（或 uvm_object）不在 testbench 层次中，只能做 type override。

> 记忆：type = 一类全换；instance = 只换某一个；非组件对象只能 type。

### Q52. 什么是 objection？有什么用？

**uvm_objection** 类提供在多个组件和 sequence 间**共享一个计数器**的机制：

- 每个组件/sequence 可异步地 **raise**（抬升）和 **drop**（放下）objection，使计数器增减。
- 当计数器从非零变为零，即发生 **"all dropped"** 状态。

**最常见用途**：在 UVM phase 机制中协调**每个运行期 phase 的结束**。phase 中启动的用户进程先 raise objection，进程完成后 drop；当该 phase 内所有进程都 drop 后，objection 计数归零，"all dropped" 通知 phase 机制：所有参与者都同意该 phase 可以结束。

```systemverilog
task main_phase(uvm_phase phase);
  phase.raise_objection(this);   // 抬升 objection，阻止 phase 提前结束
  my_test_sequence.start(my_sequencer);
  phase.drop_objection(this);    // 完成工作后放下 objection
endtask
```

> 记忆：raise = 举手"我还有活"；drop = 放手"我干完了"；全放完 phase 才结束。

### Q53. 如何实现仿真超时机制？

仿真超时机制用于：当测试因某个 bug 在最大时间后仍无进展时，强制停止仿真。

- **set_global_timeout(timeout)**：便捷函数，把超时值设置到 `uvm_top.phase_timeout` 变量。若 run() phase 在该超时值前未结束，仿真被停止并报告错误。
- 在启动测试的顶层 module 中调用：

```systemverilog
module test;
  initial begin
    set_global_timeout(1000ns);
  end
  initial begin
    run_test();
  end
endmodule
```

### Q54. 什么是 phasing？

与模块化 testbench（所有模块静态存在于层次中）不同，基于类的 testbench 需要管理不同对象的创建以及其中各种 task/function 的执行。**Phasing** 是类化 testbench 中保持**一致的执行流程**的重要概念。一次测试执行可概念上分为：配置 → 创建 testbench 组件 → 运行期激励 → 测试结束检查，UVM 为每类定义了标准 phase。

### Q55. UVM 组件有哪些 phase？run_phase() 有哪些子 phase？

UVM 用标准 phase 给仿真期间的主要步骤排序，分为三组，按以下顺序执行：

**1. Build phases（构建期，不耗仿真时间）** —— 配置并构造 testbench：

1. `build_phase()`
2. `connect_phase()`
3. `end_of_elaboration()`

**2. Run time phases（运行期，可消耗时间）** —— 大部分测试执行发生在这里：

1. `start_of_simulation()`
2. `run_phase()` —— 又细分为 **12 个子 phase**：
   - pre_reset → reset → post_reset
   - pre_configure → configure → post_configure
   - pre_main → main → post_main
   - pre_shutdown → shutdown → post_shutdown

**3. Clean up phase（收尾期）** —— 测试结束后收集并报告结果与统计：

1. `extract()`
2. `check()`
3. `report()`
4. `final()`

> 记忆：**建-连-详（build/connect/end_of_elaboration）→ 起-跑（start_of_simulation/run）→ 提-查-报-终（extract/check/report/final）**；run 的 12 个子 phase 是 4 段式（reset/configure/main/shutdown），每段前加 pre-、后加 post-。

### Q56. 为什么 build_phase() 在组件层次中自顶向下执行？

所有 testbench 组件（test、Env、Agent、Driver、Sequencer）都基于 uvm_component 类，且存在层次关系。`build_phase()` 用于**从父组件构造所有子组件**：要搭建 testbench 层次，必须先有父对象，父对象再构造子对象，子对象再继续构造孙对象。因此 **build_phase() 总是自顶向下执行**。

例如：顶层 uvm_test 的 build_phase 构造所有 uvm_env；每个 uvm_env 的 build_phase 构造其所有 uvm_agent，依此类推。其他 phase 的执行顺序无关紧要；所有组件的 `run_phase()` 是**并行**执行的。

> 注意：只有 build_phase 要求自顶向下；run_phase 是并行的。

### Q57. phase_ready_to_end() 有什么用？

**phase_ready_to_end(uvm_phase phase)** 是组件类中的**回调方法**，当对应 phase 的所有 objection 都被 drop、phase 即将结束时被调用。组件可用它定义 phase 即将结束时需要执行的功能：

- 例如：即使所有 objection 已 drop，仍希望**延迟 phase 结束**直到某条件满足。
- 例如：若有 irritator 或 reactive sequence 一直运行直到 main sequence 完成，可在 main_phase 的 `phase_ready_to_end()` 回调中**停止这些 irritator sequence**。

### Q58. uvm_config_db 是什么？用来做什么？

**uvm_config_db** 是 UVM 的配置数据库，支持在不同 testbench 组件间**共享配置和参数**。任何组件都可以把变量、参数、对象句柄等放入配置数据库；其他组件**无需知道配置在层次中的位置**就能获取。

典型例子：顶层 testbench module 把 virtual interface 指针放入 uvm_config_db，任何 uvm_driver 或 uvm_monitor 组件都能查询 uvm_config_db 获取该 virtual interface 句柄，从而通过接口访问信号。

### Q59. uvm_config_db 的 get() 和 set() 方法怎么用？

- **set()**：向 config_db 填充配置信息，并可控制哪些组件能看见该信息（全局可见或仅对某个/某些组件可见）。
- **get()**：从数据库查找匹配参数的共享配置。

语法：

```systemverilog
uvm_config_db#(<type>)::set(uvm_component context, string inst_name, string field_name, <type> value);
uvm_config_db#(<type>)::get(uvm_component context, string inst_name, string field_name, ref value);
```

参数含义：

- **context**：调用 get/set 的当前类或组件；
- **inst_name**：调用 get/set 的组件实例名；
- **field_name**：在 config_db 中设置/获取的对象、参数或变量名；
- **<type>**：配置信息的类型（对象句柄用类名，其他变量用其类型）。

### Q60. 低层组件能把句柄传给高层组件吗？

**不推荐**。UVM 中通常的配置流向是：**高层组件把句柄设置进配置数据库，低层组件用 get/set 方法获取**。

### Q61. 给组件分配 virtual interface 的推荐做法？

顶层 testbench module（实例化 DUT 和接口）把 virtual interface 设置进 uvm_config_db；之后 test 类或组件层次中任何组件用 get() 查询该 virtual interface 句柄来访问信号。

```systemverilog
module test;
  logic pclk;
  logic [31:0] paddr;
  // 实例化一个 APB 总线主设备 DUT
  apb_master apb_master(.pclk(pclk), *);
  // 实例化 APB 接口的物理接口
  apb_if apb_if(.pclk(pclk), *);
  initial begin
    // 把物理接口传给 test 类顶层，
    // 再由它向下传给 env -> agent -> drv/sqr/mon
    uvm_config_db#(virtual apb_if)::set(null, "uvm_test_top", "vif", apb_if);
  end
endmodule
```

env 类中取回并向下传递：

```systemverilog
class apb_env extends uvm_env;
  `uvm_component_utils(apb_env);
  apb_agent agt;              // ENV 类以 agent 为子组件
  virtual apb_if vif;         // APB 接口的 virtual interface

  // build phase：构造 agent，并从 test 获取 virtual interface 句柄传给 agent
  function void build_phase(uvm_phase phase);
    agt = apb_agent::type_id::create("agt", this);
    if (!uvm_config_db#(virtual apb_if)::get(this, "", "vif", vif)) begin
      `uvm_fatal("config_db_err", "No virtual interface specified for this env instance");
    end
    uvm_config_db#(virtual apb_if)::set(this, "agt", "vif", vif);
  endfunction : build_phase
endclass : apb_env
```

> 记忆：顶层 set → 各层 get → 需要处 set 向下传（自上而下的配置流）。

### Q62. 仿真在 UVM 中如何结束？

UVM 是分 phase 执行（build → run → check）。run() phase 是实际仿真发生的阶段，期间每个组件在开始时 raise objection 并保持到活动完成；**所有组件都 drop objection 后 run() phase 完成**，随后所有组件的 check() phase 执行，测试结束。

此外还有超时控制：run() phase 开始时同时启动一个并行超时定时器。若定时器在 run() phase 完成前达到超时限制，run() phase 超时、报错，然后执行 run() 之后的所有 phase，测试结束。

### Q63. 什么是 UVM RAL？

**UVM RAL（Register Abstraction Layer，寄存器抽象层）** 是 UVM 支持的特性，帮助用**抽象寄存器模型**验证设计中的寄存器，以及配置 DUT。寄存器模型提供：

- 跟踪 DUT 寄存器内容的方式；
- 访问 DUT 内寄存器和存储位置的便捷层；
- 抽象结构反映设计规格中的寄存器结构（硬件和软件工程师的共同参考）。

其他特性：支持寄存器初始化的**前门（front door）和后门（back door）** 访问，以及内置功能覆盖率支持。

> 记忆：RAL = 寄存器/存储器的抽象模型 + 前后门访问 + 内置覆盖率。

### Q64. 什么是 UVM callback？

**uvm_callback** 类是回调的基类，用于**在不修改组件类的情况下修改或增强组件行为**。典型流程：组件开发者定义从 uvm_callback 派生的应用专用回调类，在其中定义一个或多个虚方法（即**回调接口**），用于覆盖组件类的行为。

常见用法：在 driver 把生成的报文发给 DUT 之前注入错误。伪代码示例：

```systemverilog
class Packet_c;
  byte [4] src_addr, dst_addr;
  byte data[];
  byte [4] crc;
endclass

// 从基类派生的用户自定义回调类
class PktDriver_Cb extends uvm_callback;
  function new(string name = "PktDriver_Cb");
    super.new(name);
  endfunction
  virtual task corrupt_packet(Packet_c pkt);
    // 实现如何破坏报文
    // 例如翻转 CRC 第 0 字节的第 0 位
    pkt.crc[0][0] = ~pkt.crc[0][0];
  endtask
endclass : PktDriver_Cb

// 主 driver 类
class PktDriver extends uvm_component;
  `uvm_component_utils(PktDriver)
  // 把回调类注册到 driver
  `uvm_register_cb(PktDriver, PktDriver_Cb)
  function new(string name, uvm_component parent = null);
    super.new(name, parent);
  endfunction
  virtual task run();
    forever begin
      seq_item_port.get_next_item(pkt);
      // 按概率旋钮执行回调，注入报文损坏
      `uvm_do_callbacks(PktDriver, PktDriver_Cb, corrupt_packet(pkt))
      // 其他驱动到 DUT 的代码
    end
  endtask
endclass
```

> 记忆：callback = 不改组件类、用钩子注入行为（错误注入、激励修饰）；宏三件套 `uvm_register_cb` + `uvm_do_callbacks`。

### Q65～Q66. uvm_root 是什么？uvm_test 的父类是谁？

- **uvm_root**：所有 UVM 组件的**隐式顶层和 phase 控制器**。用户不直接实例化 uvm_root，UVM 自动创建唯一实例，可通过全局变量 **uvm_top** 访问。
- **uvm_test**：用户可实现的最顶层类，没有显式声明的父类；UVM 将特殊组件 **uvm_top** 分配为 test 类的父类。

## 6.2 形式验证（Formal Verification）

### Q67. 什么是形式验证？

**形式验证（Formal Verification）** 是用**数学模型**验证设计实现满足规格的过程，通过数学推理和算法**证明**设计符合规格。在形式验证中，**所有用例（输入和状态）都被工具隐式覆盖**，无需开发激励生成器或期望输出。工具需要的是用属性（property）或高层模型表示的**规格的形式化描述**，以便穷举所有输入组合来证明或证伪功能正确性——SystemVerilog property 可用于形式化描述设计规格。

> 背景：动态仿真只能提高设计正确性的置信度，永远无法 100% 完备；形式验证能针对规格全面证明设计的正确性，但复杂度受设计规模限制，因此通常选择适当的功能区域做形式验证。

### Q68. 形式验证是静态验证还是动态验证？

**静态验证（Static Verification）**——不运行任何动态仿真周期。

### Q69. 形式验证有哪两种方法？

1. **Model Checking（模型检验）**
2. **Formal Equivalence（形式等价性检查）**

### Q70. 什么是 Model Checking？

**Model Checking** 中，待验证的模型被描述为一组**从设计规格推导出的属性**。工具**穷举搜索设计的状态空间**，检查所有属性在所有状态下是否成立；任何状态下属性被违反都会报错。

> 记忆：Model Checking = 对**一个模型**穷举状态空间，证属性；属性来自规格。

### Q71. 什么是 Formal Equivalence？

**Formal Equivalence** 用于验证**两个模型**（相同或不同抽象层次）功能上是否相同。它不回答"模型功能是否正确"，只回答"两个模型功能是否等价"。最常用于对比 **RTL 设计与综合后的网表**，也可用于两个 RTL 模型或两个门级模型之间。

> 记忆：Equivalence = 两两对比，证"一样"，不证"对"。

### Q72. 哪些验证条件下可用 Formal Equivalence？

1. RTL 设计 & 综合后网表（门级模型）
2. RTL 设计 & 参考模型（reference model）
3. 两个 RTL 设计
4. 两个门级模型
5. 两个参考模型

### Q73. 形式验证相对动态验证有哪些优点？

1. **穷举验证**：动态仿真靠生成器/测试产生激励，无法穷举；形式验证由工具自动生成激励去证明/证伪所有规格，覆盖**穷举状态空间**。
2. **无需生成激励**：穷举激励由工具自动生成，用户的工作只是用属性实现形式化规格。
3. **无需生成期望输出**：设计正确性由数学保证。

### Q74. 形式验证有哪些局限？

1. **可扩展性（最大的局限）**：仅适用于较小设计——每增加一个触发器，状态空间翻倍（输入场景加倍）。
2. **只保证相对规格的正确**：不保证设计真的能工作（比如**规格本身有 bug** 时）。
3. **Model Checking 需要把规格翻译/编码成属性**。

### Q75. 形式上验证过的模块还需要覆盖率数据吗？

**不需要**。形式验证在数学上保证设计意图在所有可能的输入条件下都被验证，因此无需该模块的覆盖率数据。

## 6.3 功耗与时钟（Power and Clocking）

> 背景：当今低功耗 ASIC/SoC 设计支持 Power Gating（电源门控）、DVFS、多电压域、多电源域，因此**功耗感知验证**和**跨时钟域（CDC）验证**是设计验证流程的重要组成部分。

### Q76. CMOS 电路功耗的主要组成？

1. **动态功耗（Dynamic Power）**：由电容充放电导致的翻转引起。
2. **静态功耗（Static Power）**：无翻转（空闲状态）时由**漏电流**引起。

### Q77. 什么是动态功耗？依赖哪些参数？

动态功耗 PD 是**容性负载功耗（Pcap）**与**瞬态功耗（PTransient）**之和，正比于 **CV²f**：

```
PD = Pcap + PTransient
PD = A(CL + C)·Vdd²·f
```

| 参数 | 含义 |
|---|---|
| A | 活动因子（Activity Factor，电路翻转的比例） |
| C | 内部电容（Internal Capacitance） |
| CL | 负载电容（Load Capacitance） |
| Vdd | 供电电压 |
| f | 工作频率 |

### Q78. 什么是静态功耗？依赖哪些参数？

**静态功耗**是电路无翻转活动时消耗的功耗，即**漏电功耗**（例如开机后电池因电流流动而耗电）：

```
Pstatic = Istatic × Vdd
```

其中 Vdd 为供电电压，Istatic 为流过器件的总电流。

> 记忆：动态功耗 ∝ CV²f（靠翻转产生）；静态功耗 = I·V（靠漏电产生）。

### Q79. 什么是多电压域（Multi-Voltage Domain）？为什么需要？

**多电压域**是低功耗设计技术，设计中有**多个电压域**，目标是"为所需性能优化功耗"。电压越高电路越快（性能越高），但动态功耗也越高（正比于 CV²f）。有些设计中只有少数部分需要高频运行，其余部分可低频运行——给这些部分**供较低电压**即可省功耗。

### Q80. 什么是 DVFS？什么时候用？

**DVFS（Dynamic Voltage Frequency Scaling，动态电压频率缩放）** 是低功耗设计技术，**动态调节功耗以适应所需频率**：以设计正常运行所需的最小频率和/或电压来修改工作频率和电压。之所以叫"动态"，是因为该过程发生在设计**运行期间**。

- 传统省电方式：以工作频率运行，空闲时周期性关电。
- DVFS：在相同工作量下，用较低频率运行换取性能，可节省更多功耗；省电还来自电压的**二次方关系**（P ∝ V²）。运行时根据完成任务所需的性能选择频率，让空闲时间更长但以更低电压运行，从而省电。

> 记忆：DVFS = 运行期按需降压降频；省电收益中电压是平方级的。

### Q81. 什么是 UPF？

**UPF（Unified Power Format）** 是 **IEEE 1801** 标准，用于指定设计的**功耗意图（power intent）**，例如：应布设哪些电源轨、设计各模块何时上电/下电、信号跨电源域时电压电平如何变化、隔离单元及对应的钳位值、存储器保持（retention）等。

### Q82. 什么是功耗感知仿真？为什么重要？

**功耗感知仿真（Power Aware Simulation）** 指在 **RTL 和/或 GLS（门级仿真）** 层面建模**下电/上电行为**。其重要性：

1. 尽早发现功耗相关的 RTL/规格 bug——关键功耗 bug 会导致芯片不可用。
2. 电源管理至关重要，现代 ASIC/SoC 有大量为实现电源管理而实现的逻辑。

### Q83. 什么是电源域（Power Domain）？

**电源域**是**共享同一主供电组（primary supply set）** 的设计元素集合，即按共同功耗策略（工作电压、供电网络、上/下电条件等）分组的设计部分。

### Q84. 设计中为什么需要电平转换器（Level Shifter）？

当设计中存在**多个电压域**时，逻辑信号从一个电压域进入另一个电压域时，需要用**电平转换器**把信号从一种电压电平转换为另一种电压电平，使信号逻辑值在不同电压域中能被正确解释。

### Q85. 什么是隔离（Isolation）？

**隔离**是控制**进出已下电电源域的信号行为**的技术：当电源域下电时，把信号**钳位到已知值（1、0）**，或**锁存到先前值**。

> 记忆：隔离 = 下电域边界的"守门员"，把浮空信号钳成确定值。

### Q86. 什么是亚稳态？何时发生？有什么后果？

**亚稳态（Metastability）** 是电路**无法在正常工作所需时间内稳定到逻辑 "0" 或 "1"** 的状态，通常由**建立时间/保持时间违例**引起。后果：

1. 导致不可预测的系统行为。
2. 不同的扇出锥可能读到不同的信号值，使设计进入未知状态。
3. 不稳定的数据（"0"/"1"）传播到设计各处可能引起大电流，最终导致**芯片烧毁**。

### Q87. 如何避免亚稳态？

用**同步器（synchronizer）**。同步器保证不稳定振荡（"0"/"1"）有足够时间稳定下来，从而得到稳定输出。

### Q88. 基本同步器电路长什么样？

基本同步器是**两级触发器同步器（two flip-flop synchronizer）**：第一级触发器等待一个时钟周期，让输入的亚稳态稳定/消退；第二级触发器在输出端提供稳定信号。

- 注意：第一级触发器输出在信号被采入第二级时仍可能不稳定（使第二级输出亚稳态），此时可用**三级触发器同步器**。
- 但通常**两级触发器同步器**足以消除亚稳态。

> 记忆：2-FF 同步器是标准答案；极端场景升级到 3-FF。

### Q89. 什么是时钟门控（Clock Gating）？

**时钟门控**是省电技术：**关闭设计中非活动部分的时钟供给**，控制时钟网络消耗的功耗，通过避免不必要的翻转活动来降低动态功耗。

### Q90. 什么是电源门控（Power Gating）？为什么使用？

**电源门控**是省电技术：**关闭设计中不使用部分的电源**，切断逻辑空闲时的静态漏电，从而降低功耗。

> 对比记忆：**时钟门控省动态功耗，电源门控省静态功耗**。

### Q91. 多时钟域设计的 CDC 会遇到哪些问题？

跨时钟域（CDC）最常见的问题（验证工程师必须熟悉）：

1. **亚稳态导致同步失败**：不同时钟域频率不同，当一域的信号在另一域时钟有效沿附近被采样时，输出可能进入亚稳态，导致同步失败。
2. **数据不一致（Data Incoherency）**：若未用合适设计技术，目的时钟域可能收到不一致的数据。例如多信号同时变化地跨域传输，源/目的有效沿又接近时，部分信号在某个周期被捕获、部分在另一周期被捕获，导致数据不一致。
3. **数据丢失（Data Loss）**：若未用合适技术，CDC 边界可能丢数据。例如信号从快时钟域传到慢时钟域，且信号宽度只有（快时钟的）一个周期，若该信号恰在慢时钟有效沿之间到达，信息就可能被漏掉。

> 记忆：CDC 三大问题 = **亚稳态（同步失败）、数据不一致、数据丢失**。

### Q92. 如何同步两个时钟域之间的信号？有哪些设计技术？

按传输位宽分两类：

**1-bit 跨域：**

1. 接收（目的）时钟域用 **2-FF 或 3-FF 同步器**。
2. **闭环同步器（closed-loop synchronizer）**：从目的时钟域向源时钟域发送**反馈/应答信号**。

**多 bit 跨域：**

1. 为多 bit 建立**多周期路径（MCP）**：源域未同步信号连同**同步过的控制信号**一起发送到目的域。
2. **格雷码（Gray Code）编码**：格雷码每次只允许 1 bit 变化，可应对亚稳态问题。
3. **异步 FIFO**（源域写入、目的域读出）：**最安全的技术之一**，提供与时钟频率无关的完整同步。
4. 把多 bit 合并成 **1-bit CDC 信号**，再用 2-FF 同步器或闭环同步器处理。

> 记忆：1-bit → 2/3-FF 或闭环应答；多 bit → MCP+控制信号 / 格雷码 / 异步 FIFO（最安全）。

### Q93. 从快时钟域向慢时钟域传数据会出什么问题？

信号从快域传到慢域、且信号宽度只有（快时钟的）一个周期时，若该信号在慢时钟有效沿之间到达，信息可能被**漏掉（数据丢失）**。

### Q94. 异步复位的优缺点？

**优点：**

1. 异步复位优先级最高。
2. 保证数据路径干净。
3. 有无时钟信号时都能生效。

**缺点：**

1. 若异步复位在时钟有效沿（附近）释放，触发器输出可能进入**亚稳态**。
2. 对**毛刺敏感**，可能引起误复位。

### Q95. 同步复位的优缺点？

**优点：**

1. 复位发生在时钟有效沿，保证电路 100% 同步。
2. 在基于周期的仿真器中更容易处理。
3. 通常综合出更小的触发器，节省芯片面积。

**缺点：**

1. 可能需要**脉冲展宽器**，使其足够宽以便在有效沿被看到。
2. 会**增加额外组合逻辑**。
3. 复位需要时钟存在；若电路有内部三态总线，需要单独的异步复位以防止三态总线冲突。

> 记忆：异步复位 = 快、优先级高、但怕亚稳态和毛刺；同步复位 = 稳、省面积、但要多逻辑、需时钟、可能要展宽。

### Q96. 什么是复位恢复时间（Reset Recovery Time）？为什么重要？

**复位恢复时间**是**复位释放与时钟信号变高之间**的时间。若复位释放后很短时间内时钟变高，可能引起**亚稳态**——因为复位释放后变活跃的所有信号，在下一个触发器输入端将不满足时序条件。

### Q97. 什么是频率合成器？举例。

**频率合成器**是从一个稳定的参考频率**产生新频率**的电路。例如：从 100 MHz 参考时钟产生 200 MHz 时钟，常用 **PLL** 作为频率合成器。

### Q98～Q99. 什么是 PLL？

**PLL（Phase Locked Loop，锁相环）** 是一个反馈电子电路（准确说是控制系统），用于产生**相位与输入信号相位相关**的输出信号。可用于相位/频率调制解调，也可作频率合成器。PLL 由三个功能块组成：

1. **鉴相器（Phase Detector）**
2. **环路滤波器（Loop Filter）**
3. **压控振荡器（Voltage Controlled Oscillator, VCO）**

用 PLL 做频率合成时：参考频率 fr 与输出频率 fo 满足 **fr = fo/N，即 fo = N·fr**（输出频率是参考频率的 N 倍）。

> 记忆：PLL 三件套 = 鉴相器 + 环路滤波器 + VCO；倍频 N 倍靠分频器反馈。

## 6.4 覆盖率（Coverage）

> 背景：覆盖率定义为**已完成的验证目标百分比**，是评估验证项目进展的度量，也是约束随机 testbench 进度与质量反馈的关键。两大类：**代码覆盖率**（仿真器自动生成）与**功能覆盖率**（用户自定义，通常用 SystemVerilog 构造实现）。

### Q100. 代码覆盖率与功能覆盖率的区别？

| | 代码覆盖率（Code Coverage） | 功能覆盖率（Functional Coverage） |
|---|---|---|
| 度量对象 | 设计代码（HDL 模型）被测试套件执行的程度 | 设计规格中（测试计划枚举的）功能被激励的程度 |
| 来源 | 仿真器开启后**自动提取** | **用户自定义**，不能自动推断 |
| 依赖 | 依赖设计代码 | 不依赖设计代码，基于设计规格实现 |
| 用途 | 判断代码是否都被跑到 | 判断感兴趣场景、边界情况、规格不变量等是否被观察到并验证 |

### Q101. 代码覆盖率有哪些类型？

1. **语句/行覆盖率（Statement/Line）**：统计仿真中覆盖了多少条语句（行）。一般要求验证收口时达到 100%。

```systemverilog
always @(posedge clk) begin
  if (A > B) begin
    Result = A - B;   // Line 1
  end else begin      // Line 3
    Result = A + B;   // Line 4
  end
end
```

2. **块覆盖率（Block）**：begin-end、if-else、case、while、for 等包围的一组语句称为一个块；块覆盖率度量这些块是否被执行。与语句覆盖率相似，但关注的是**一组语句**（上例中有 3 个 begin…end 块）。
3. **分支/判定覆盖率（Branch/Decision）**：评估 if-else、case、三元运算符（?:），度量**真、假两个分支**是否都被覆盖（上例中 if (A>B) 为单一分支，测其真/假）。
4. **条件覆盖率与表达式覆盖率（Conditional/Expression）**：
   - 条件覆盖率：统计 HDL 中所有布尔表达式为真/假的次数。
   - 表达式覆盖率：看赋值**右端**，把各种可能情况按真值表求值，度量这些情况被覆盖得如何。例如 `Result = (A && B) || (C)`，可对 A/B/C 建真值表，表达式覆盖率衡量真值表各行是否都被覆盖。
5. **翻转覆盖率（Toggle）**：度量仿真期间设计信号和端口的翻转程度，也能帮助发现从不改变值的未使用信号。
6. **FSM 覆盖率**：度量状态机所有状态和所有可能转移/弧是否在仿真中被覆盖。

> 记忆：代码覆盖率六类 = **语句、块、分支、条件/表达式、翻转、FSM**。

### Q102. 高功能覆盖率 + 低代码覆盖率说明什么？

代码覆盖率由仿真器自动提取，功能覆盖率是用户自定义。**低代码覆盖率 + 高功能覆盖率**可能的原因：

1. 设计中有大量按规格实现功能**用不到的代码**（死代码，dead code）。
2. 用户定义的功能覆盖率度量有误：测试计划没覆盖全部设计功能/场景/边界，或对应的功能覆盖率监视器实现缺失。
3. 功能覆盖率监视器实现有 bug，导致**虚假覆盖**。

> 注意：因此验证项目中应充分评审用户定义的功能覆盖率指标及其实现。

### Q103. 高代码覆盖率 + 低功能覆盖率说明什么？

可能的原因：

1. 设计中**未按规格实现全部功能**，对应代码缺失，而功能覆盖率指标存在但无测试跑到。
2. 功能覆盖率监视器实现有 bug，即使测试在跑、在设计代码上确实产生了激励，也不被计入覆盖。
3. 可能存在覆盖所有功能的测试和激励，但因某些 bug **失败而被排除**在功能覆盖率度量之外。

### Q104. 功能覆盖率在 SystemVerilog 中的两种实现构造？

1. **covergroup（覆盖组）**：度量仿真期间给定信号或表达式出现指定值或值集合的次数；还可通过 **cross** 度量不同事件/值同时出现。与类相似，定义后可用 `new()` 创建实例。covergroup 可定义在 **package、module、program、interface、checker 或 class** 中。
2. **cover property（覆盖属性）**：度量**跨时间的事件序列**出现次数，使用与写断言的 property/sequence 相同的时序语法。

### Q105. covergroup 能在类中定义和使用吗？

**可以**。在类内定义 covergroup 是度量类属性覆盖的非常有效的方式，可用于基于 testbench 构造（事务、sequence、checker、monitor 等）实现功能覆盖率。

### Q106. 什么是 coverpoint 和 bins？

- **coverpoint（覆盖点）**：指定一个需要覆盖的**整型表达式**的构造。一个 covergroup 可有多个 coverpoint 覆盖不同表达式/变量。
- **bins（仓）**：每个 coverpoint 包含一组 bins，即该表达式/变量被采样的不同值。bins 可由用户显式定义，也可由语言**自动创建**。

```systemverilog
bit [2:0] a;
bit [3:0] b;
covergroup cg @(posedge clk);
  cp_a : coverpoint a {
    bins values_a = {[0, 1, 3, 5, 7]};  // 用户自定义 bins，只看这些值
  }
  cp_b : coverpoint b;                  // 自动 bins，覆盖 b 的所有可能值
endgroup
```

### Q107. 下面 coverpoint cp_a 创建了多少个 bins？

```systemverilog
bit [3:0] var_a;
covergroup test_cg @(posedge clk);
  cp_a : coverpoint var_a {
    bins low_bins[] = {[0:3]};     // 展开为 4 个 bin，每个 bin 各看一个值（0~3）
    bins med_bins  = {[4:12]};     // 1 个 bin，覆盖 4~12 中任意值
  }
endgroup
```

**答案：5 个 bins**。`low_bins[]` 带数组后缀展开成 4 个 bin（分别对应 0、1、2、3），`med_bins` 是 1 个 bin（4~12 任一值命中即覆盖）。

### Q108. ignore_bins 与 illegal_bins 的区别？

- **ignore_bins**：显式**排除**一组值或转移，不参与覆盖率统计：

```systemverilog
coverpoint a {
  ignore_bins ignore_vals = {7, 8};  // 忽略采样值 7 和 8
}
```

- **illegal_bins**：把一组值或转移**标记为非法**；一旦出现**运行时错误**：

```systemverilog
covergroup cg3;
  coverpoint b {
    illegal_bins bad_vals = {1, 2, 3};  // 采样到 1/2/3 即报运行时错误
  }
endgroup
```

> 注意：**illegal_bins 优先级高于其他所有 bins**——即使某值同时出现在其他 bin 中，采到它照样报错。

### Q109. 如何写转换覆盖率（transition coverage）的 coverpoint？

转换覆盖率写作 **"value1 => value2"**，value1 和 value2 是表达式在两个**连续采样点**的采样值：

```systemverilog
covergroup cg @(posedge clk);
  coverpoint v_a {
    bins sa = (4 => 5 => 6);   // 连续三个正沿依次采到 4、5、6
  }
endgroup
```

### Q110. 下面 coverpoint 覆盖了哪些转换？

```systemverilog
coverpoint my_variable {
  bins trans_bin[] = (a, b, c => x, y);
}
```

展开为覆盖所有组合：**a=>x, a=>y, b=>x, b=>y, c=>x, c=>y**（笛卡尔积）。

### Q111. 下面 bin 想覆盖什么？

```systemverilog
covergroup test_cg @(posedge clk);
  coverpoint var_a {
    bin hit_bin = {3[*4]};
  }
endgroup
```

`[*N]` 是**连续重复**运算符：该 bin 想覆盖信号 var_a 在连续 4 个采样点（clk 正沿）上**连续出现 4 次值 3** 的转移。

### Q112. 什么是 wildcard bins？

- 默认情况下，值/转移 bin 可定义 4 态值；bin 定义中含 X 或 Z 时，表示只有采样值在相同位上是 X/Z 才计数（用 `===` 比较）。
- **wildcard bin** 使定义中所有 **X、Z 或 ?** 都作为 0 或 1 的**通配符**：

```systemverilog
coverpoint a[3:0] {
  wildcard bins bin_12_to_15 = {4'b11??};  // 低两位不关心
}
```

`bin_12_to_15` 中低两位是 don't care，因此采样值为 1100、1101、1110、1111 任一都命中同一 bin。

### Q113. 什么是交叉覆盖率（cross）？何时有用？

covergroup 可以指定两个或更多 coverpoint/变量之间的交叉覆盖率，用 **cross** 构造。N 个 coverpoint 的交叉覆盖率定义为这 N 个 coverpoint 所有 bins 的**所有组合**（即 N 组 bins 的**笛卡尔积**）：

```systemverilog
bit [31:0] a_var;
bit [3:0]  b_var;
covergroup cov3 @(posedge clk);
  cp_a : coverpoint a_var {
    bins yy[] = {[0:9]};      // 10 个 bins
  }
  cp_b : coverpoint b_var;    // 4 bit 变量 → 16 个 bins
  cc_a_b : cross cp_b, cp_a;  // 交叉覆盖率
endgroup
```

上例中 cp_a 有 10 个 bins（0~9），cp_b 有 16 个 bins，交叉覆盖率共有 **16×10 = 160 个 bins**。

要点：

- cross 也可在 coverpoint 与**变量**之间定义，此时系统为该变量隐式创建 coverpoint。
- **cross 只允许在同一个 covergroup 内**的 coverpoint 之间进行。
- 用途：确保多个事件/表达式采样值**同时发生**——很多场景要测多个功能/事件同时出现，cross 保证所有组合都被验证。

### Q114. 下面 cross 覆盖率创建了多少个 bins？

```systemverilog
bit [1:0] cmd;
bit [3:0] sub_cmd;
covergroup abc_cg @(posedge clk);
  a_cp      : coverpoint cmd;
  cmd_x_sub : cross cmd, sub_cmd;
endgroup
```

- `a_cp` 生成 **4 个自动 bins**（cmd 是 2 bit）。
- cross 一个 coverpoint 与一个变量时，SystemVerilog 为变量创建隐式 coverpoint：sub_cmd 隐式 coverpoint 有 **16 个自动 bins**。
- 因此交叉覆盖率生成 **4 × 16 = 64 个 bins**。

### Q115. 下面覆盖率代码有什么问题？

```systemverilog
int var_a;
covergroup test_cg @(posedge clk);
  cp_a : coverpoint var_a {
    bins low   = {0, 1};
    bins other[] = default;   // 危险用法！
  }
endgroup
```

**问题**：coverpoint 采样的是 int（2³² 个可能值）。第一个 bin 只看 0 和 1，第二个用 `default` 的 bin 会为其余所有值（2³²−2 个）各建一个 bin，**bin 数量巨大，可能导致仿真器崩溃**。

> 注意：`default` 用法应尽量少用或谨慎使用。

### Q116. covergroup 有哪几种采样方式？

1. **在 covergroup 定义中指定时钟事件**：事件触发时采样所有 coverpoint：

```systemverilog
covergroup transaction_cg @(posedge clk);
  coverpoint req_type;
endgroup
```

2. **显式调用预定义的 sample() 方法**：不想每个时钟沿（或高频事件）都采样时（因为被采样的表达式/变量变化不频繁），可在信号/表达式变化时显式调用 `sample()`。类内定义的 covergroup 尤其常用：

```systemverilog
class packet;
  byte [4] dest_addr;
  byte [4] src_addr;
  covergroup pkt_cg;
    coverpoint dest_addr;
  endgroup
  function new();
    pkt_cg = new();       // 构造函数中实例化 covergroup
  endfunction
endclass

module test;
  initial begin
    packet pkt = new();
    pkt.pkt_cg.sample();  // 每创建一个新报文就采样一次
  end
endmodule
```

### Q117. 如何给 covergroup 传参数？何时有用？

covergroup 可像 task/function 一样带参数；信号可用 **ref** 关键字传入。用处：定义**通用 covergroup**，对多个实例传不同信号/变量复用：

```systemverilog
module test;
  covergroup xy_cg(ref int x, ref int y, input string name);
    cp_x : coverpoint x;
    cp_y : coverpoint y;
    cc_x_y : cross cp_x, cp_y;
  endgroup
  initial begin
    xy_cg xy_cg_mod1 = new(top.mod1.x, top.mod1.y, "mod1_cvg");
    xy_cg xy_cg_mod2 = new(top.mod2.x, top.mod2.y, "mod2_cvg");
  end
endmodule
```

### Q118. covergroup 内的 coverpoint 能引用设计的层次信号吗？

**可以**。covergroup 内的 coverpoint 可通过层次引用设计中的信号。

### Q119. 不同 covergroup 的 coverpoint 之间能做 cross 吗？

**不能**。cross 只可能发生在**同一个 covergroup** 内的 coverpoint 之间。

### Q120. per-instance 与 per-type 覆盖率的区别？

一个 covergroup 可被定义并实例化多次。默认情况下，多个实例的覆盖率按**该 covergroup 类型**汇总（cumulative）报告。可在 covergroup 内设置 **option.per_instance = 1**，此后 SystemVerilog 为**每个实例单独**报告覆盖率：

```systemverilog
covergroup test_cg @(posedge clk);
  option.per_instance = 1;   // 每个实例单独报告覆盖率
  coverpoint var_a;
  // 其他 coverpoint
endgroup
```

> 记忆：默认按类型汇总；设 per_instance 后按实例分报。

## 6.5 断言（Assertions）

> 背景：断言（assertion）指定系统的**行为**，主要用于验证设计行为，也可提供功能覆盖率、标记用于验证的输入激励。断言可被动态仿真检查，也可被静态属性检查/形式验证工具检查。SystemVerilog 提供丰富的 sequence 和 property 构造来实现断言。

### Q121. 什么是断言？在验证中使用断言有什么好处？

**断言**是对设计规格中属性的描述，用于验证设计行为。仿真中若被检查的属性不符合规格，断言失败；若某属性/规则被禁止出现却发生了，断言同样失败。

使用断言的好处：

1. **更早发现错误**：设计规格一被违反就捕获仿真错误。
2. **更好的可观测性**：便于调试测试失败。
3. **动态仿真与形式验证通用**。
4. **可提供功能覆盖率**：对输入激励提供功能覆盖率，并验证设计属性确实被仿真过。

### Q122. 断言有哪几种类型？

SystemVerilog 定义两种断言：**立即断言（immediate assertions）** 和 **并发断言（concurrent assertions）**。

### Q123. immediate 与 concurrent 断言的差别？

| | Immediate（立即断言） | Concurrent（并发断言） |
|---|---|---|
| 语义 | 非时序，像过程块中的语句一样**立即求值** | **时序性**，在时钟沿基于变量采样值求值 |
| 执行方式 | 在过程块中执行 | 与其他设计块**并发**执行 |
| 放置位置 | 过程块内 | module 或 interface 内 |
| 可用于 | 仅动态仿真 | 动态仿真 + 静态（形式）验证 |

简单立即断言示例（检查 a 和 b 始终相等）：

```systemverilog
always_comb begin
  a_eq_b : assert(a == b) else $error("A not equal b");
end
```

并发断言示例（若某周期 c 为高，则下一周期 a 和 b 相等）：

```systemverilog
ap_a_eq_b : assert property ((@posedge clk) c |=> (a == b));
```

### Q124. simple immediate 与 deferred immediate 断言的差别？

- **简单立即断言**：立即求值，**不等待组合表达式稳定**，因此对毛刺非常敏感——组合表达式稳定过程中断言可能多次触发，其中一些是**假失败**。
- **延迟立即断言（deferred）**：只在**时间戳末尾**、组合表达式的变量稳定后才求值，即在时间戳的 **reactive region** 求值，避免毛刺误报。

> 记忆：deferred = 等组合稳定再判，专治毛刺误报。

### Q125. 用 SVA 写 checker 相比过程代码有什么优势？

SVA 提供丰富的 sequence/property 构造，某些 checker 用 SVA 写比过程代码或类化 checker 更简单；且同一断言可复用于**静态检查工具（形式验证）**和提供**功能覆盖率**。

适合 SVA 的场景举例：

1. 检查内部设计结构，如 FIFO 上溢/下溢。
2. 检查模块间内部信号和接口（设计中内嵌断言）。
3. 标准接口协议（PCIe、AMBA、Ethernet 等）的 checker，用时序表达式易于开发。
4. 仲裁、资源饥饿、协议死锁等检查通常适合形式验证——写成断言可同时用于静态和动态仿真。

### Q126. 为设计单元写断言有哪几种方式？

1. **直接写在设计模块内部**：多由设计工程师对内部信号/接口写断言。
2. **写在独立的 interface/module/program 中，再用 bind 绑定到目标模块/实例**：多由验证工程师采用，不修改目标模块代码。

### Q127. 什么是 sequence（用于写 SVA）？

**sequence** 是写 property/断言的基本构建块：可以是在单个时钟沿求值的简单布尔表达式，也可以是跨多个周期求值的事件序列。一个 property 可检查从不同时刻开始的多个时序行为，因此可由多个 sequence 逻辑组合或时序组合而成。

基本语法：

```systemverilog
sequence name_of_sequence;
  <boolean expression>
endsequence
```

示例：每个 clk 正沿采样 a、b，若二者相等则求值为真：

```systemverilog
sequence s_a_eq_b;
  @(posedge clk) (a == b);
endsequence
```

### Q128. $rose(tst_signal) 与 @posedge(tst_signal) 有区别吗？

**有区别**。

- `@posedge(tst_signal)`：**等待** tst_signal 上出现上升沿事件。
- `$rose()`：系统函数，检查信号**采样值**是否在上次采样与本次采样之间**变为 1**（上次采样可为 0/x/z）。因此 `$rose(tst_signal)` 只有在**至少存在两个采样值**时才可能返回真。

```systemverilog
sequence S1;
  @(posedge clk) $rose(a);   // 仅当 a 在两个 clk 正沿之间从 0/x/z 变为 1 时为真
endsequence
```

### Q129. 下面 sequence 何时求值为真？

```systemverilog
sequence S1;
  @(posedge clk) $rose(a);
endsequence
```

1. 当信号 a 从 0 变为 1 时。
2. 当 a 在一个 clk 正沿为 0、下一个 clk 正沿变为 1 时。
3. 当 a 在一个 clk 正沿为 1、下一个 clk 正沿为 0 时。

**答案是 2)**。$rose() 在连续两个时钟周期采样时值从 0 变为 1 才求值为真。

### Q130. sequence 可以声明在哪些地方？

可以在 **Module、Interface、Program、Clocking Block、Package** 中的任意一处声明。

### Q131. 并发断言能在类内实现吗？

**不能**。并发断言不能在类内实现。

### Q132. 下面 sequence 何时匹配？

```systemverilog
req ##2 gnt ##1 !req
```

当 `gnt` 在 `req` 为高**两个周期后**变高，再**一个周期后** `req` 被拉低为 0 时，该 sequence 匹配为真。

### Q133. 什么是重复运算符？sequence 有哪三种重复运算符？

若时序表达式需要求值多次，可用**重复运算符**构造长 sequence，而不是写超长序列。SVA 支持三种：

1. **连续重复 `[*N]`**：序列以**相邻时钟节拍**重复有限次（一次迭代结束到下一次迭代开始间隔一个时钟节拍）。

```systemverilog
a ##1 b[*5]   // a 为高后，b 连续保持 5 个周期为高
```

2. **跳转重复 `[->N]`（go-to）**：操作数布尔表达式迭代匹配有限次，**每次匹配之间间隔一个或多个时钟节拍，且中间不允许操作数再匹配**；整体重复序列在操作数**最后一次迭代匹配**处匹配。

```systemverilog
a ##1 b[->2:10] ##1 c
// 首拍 a 为真、末拍 c 为真、倒数第二拍 b 为真，
// 且从倒数第二拍起算，首末之间 b 为真的非连续节拍数至少 2、至多 10
```

3. **非连续重复 `[=N]`（non-consecutive）**：类似 go-to，但**匹配不必结束于操作数的最后一次迭代匹配**。

```systemverilog
a ##1 b[=2:10] ##1 c
// 看到 2~10 次非连续 b 之后，可以再隔若干 b 不为真的周期，然后 c 为真即可；
// 而 go-to 在 b 出现次数达到最大后，下一拍必须 c 为真
```

> 记忆：`[*]` 连续挨着来；`[->]` 最后一下必须紧接 c；`[=]` 最后一下之后可以再等。

### Q134. 下面断言有什么问题（非语法错误）？

```systemverilog
module test(input clk, input a, input b);
  assert_1 : assert(a && b);   // 立即断言写在了模块级！
endmodule
```

**问题**：立即断言只能写在**过程块（procedural block）内部**启动。

### Q135. 写一个断言：信号保持为高最少 2 个周期、最多 6 个周期。

用 property：若信号 a 上升，则从同一周期起保持为高最少 2、最多 6 个周期，且下一周期 a 变低：

```systemverilog
property a_min_2_max_6;
  @(posedge clk) $rose(a) |-> a[*2:6] ##1 (a == 0);
endproperty
assert property (a_min_2_max_6);
```

### Q136. 什么是蕴含运算符（implication operator）？

**蕴含运算符**规定：property 的检查**以时序前件（antecedent）的匹配为条件**进行。它用于给 property 表达式加前置条件，**只允许在 property 层使用**。两种：

```systemverilog
// 1) 重叠蕴含（overlapped）|-> 
assert property prop_name (sequence_expr |-> property_expr);
// 2) 非重叠蕴含（non-overlapped）|=> 
assert property prop_name (sequence_expr |=> property_expr);
```

运算符左侧叫 **antecedent（前件/前提）**，右侧叫 **consequent（后件/结论）**。antecedent 是在求值 consequent 之前必须发生的前提。

### Q137. 重叠与非重叠蕴含运算符的区别？

- **重叠蕴含（|->）**：前件匹配后，**匹配终点就是后件求值的起点**（同一周期开始检查后件）：

```systemverilog
assert property abc_overlap (@(posedge clk) (a == 1) |-> b ##1 c);
// (a==1) 匹配的同一周期 b 为真、下一周期 c 为真 → 通过
```

- **非重叠蕴含（|=>）**：后件求值起点是**前件匹配终点之后的一个时钟节拍**：

```systemverilog
assert property abc_nonoverlap (@(posedge clk) (a == 1) |=> b ##1 c);
// (a==1) 匹配后的下一周期 b 为真、再下一周期 c 为真 → 通过
```

### Q138. 蕴含运算符能用在 sequence 中吗？

**不能**，只能在 **property** 中使用。它是求值 property 表达式的前提匹配。

### Q139. 下面两个断言等价吗？

```systemverilog
1) @(posedge clk) req |=> ##2 $rose(ack);
2) @(posedge clk) req |-> ##3 $rose(ack);
```

**等价**。|-> 重叠运算符在 antecedent 为真的同一周期开始求值 consequent，|=> 非重叠运算符在 antecedent 之后一个周期开始。因此**在重叠运算符后显式加一个周期的延时**，就与非重叠运算符等价（##3 = ##1 + ##2）。

### Q140. SVA 允许嵌套蕴含吗？

**允许**。当有多个门控条件最终指向同一个结果时很有用：

```systemverilog
a |=> b |=> c
// a 为真 → 下一周期求值 b，b 为真 → 下一周期求值 c，c 为真则 property 通过
```

### Q141. $past() 系统任务做什么？

**$past** 是系统任务，能**获取前几个时钟周期的信号值**。

### Q142. 写一个断言：输出信号永远不为 X。

系统函数 **$isunknown(signal)**：信号有未知值（x）时返回 1，因此：

```systemverilog
assert property (@(posedge clk) !$isunknown(mysignal));
```

### Q143. 写一个断言：状态机的状态变量始终是 one-hot 值。

系统函数 **$isonehot()**：位向量是 one-hot 时返回真：

```systemverilog
assert property (@(posedge clk) $isonehot(state));
```

### Q144. 写一个断言：5 bit 的 grant 信号任意时刻只有 1 bit 置位。

系统函数 **$countones()** 返回信号中 1 的个数：

```systemverilog
assert property (@(posedge clk) $countones(grant[5:0]) == 1);
```

### Q145. 写一个断言：master 发出有效请求后，仲裁器在 2~5 个时钟周期内给出 grant。

```systemverilog
property p_req_grant;
  @(posedge clk) $rose(req) |-> ##[2:5] $rose(gnt);
endproperty
```

### Q146. 如何在复位有效期间禁用断言？

用 **"disable iff"** 构造显式禁用断言。下面例子在 reset 高有效时禁用检查：

```systemverilog
assert property (@(posedge clk) disable iff (reset) a |=> b);
```

### Q147. assert 与 assume 指令的区别？

- **assert**：把 property 指定为**对设计的义务（obligation）**，需要检查以验证 property 成立。
- **assume**：仿真中与 assert 相同；但它是**对环境的假设**——仿真器检查 property 是否成立，而**形式验证工具把 assume 当作约束信息来生成输入激励**。

> 记忆：assert 管设计（义务），assume 管环境（约束）；形式验证中 assume 用来限激励。

### Q148. bind 构造是做什么的？

**bind** 用于把 module/interface/checker **外部实例化（绑定）** 到目标模块或模块实例。这样封装在 module/interface/program/checker 中的仪表代码或断言，可以挂到目标模块/实例上而**不修改目标模块代码**。

语法：

```systemverilog
bind <target module/instance> <module/interface to be instantiated> <instance name with port map>;
```

示例：接口 `range` 内含断言：

```systemverilog
interface range(input clk, enable, int minval, expr);
  property crange_en;
    @(posedge clk) enable |-> (minval <= expr);
  endproperty
  range_chk : assert property (crange_en);
endinterface
```

1) 绑定到模块 cr_unit（每个 cr_unit 实例都会带一个 r1 实例）：

```systemverilog
bind cr_unit range r1(c_clk, c_en, v_low, (in1 && in2));
```

2) 只绑定特定实例 cr_unit_1：

```systemverilog
bind cr_unit:cr_unit_1 range r1(c_clk, c_en, v_low, (in1 && in2));
```

### Q149. 仿真中如何关闭所有断言？

用系统任务 **$assertoff()**：

- 不带参数：禁用所有断言。
- 仿真中途调用时，当前处于活动状态的断言允许**完成后才禁用**。
- 选择性禁用：`$assertoff[(levels[, list])]`——第一个参数指定作用多少层层次，第二个参数指定这些层次中要关闭的 property 列表。

### Q150. 给 property 指定时钟有哪几种方式？

1. **property 中使用的 sequence 实例带显式时钟**，property 使用该时钟：

```systemverilog
sequence seq1;
  @(posedge clk) a ##1 b;
endsequence
property prop1;
  not seq1;
endproperty
assert property (prop1);
```

2. **在 property 中显式指定时钟**：

```systemverilog
property prop1;
  @(posedge clk) not (a ##1 b);
endproperty
assert property (prop1);
```

3. **从使用 property 的过程块推断时钟**：

```systemverilog
always @(posedge clk)
  assert property (not (a ##1 b));
```

4. **从 clocking block 推断**（property 定义在 clocking block 内，外部通过层次引用断言）：

```systemverilog
clocking master_clk @(posedge clk);
  property prop1;
    not (a ##1 b);
  endproperty
endclocking
assert property (master_clk.prop1);
```

5. **以上都不用**：解析为**默认时钟事件（default clocking）**：

```systemverilog
default clocking master_clk;   // 如上定义的 master 时钟
  property p4;
    not (a ##1 b);
  endproperty
assert property (p4);
```

### Q151. 综合练习：深度 32 的同步 FIFO 断言

假设有 clk、write_en/read_en、full 标志、word counter 信号。

1) **word count > 31 时，FIFO full 标志置位**：

```systemverilog
assert property (@(posedge clk) disable iff (!rst_n)
                 (wordcnt > 31 |-> fifo_full));
```

2) **word count == 31 且发生一次写、没有同时读时，FIFO full 标志置位**：

```systemverilog
assert property (@(posedge clk) disable iff (!rst_n)
                 (wordcnt == 31 && write_en && !read_en |=> fifo_full));
```

> 注意：第二个断言用**非重叠蕴含（|=>）**，因为 full 标志在 write_enable 之后的下一个周期才会变高。
